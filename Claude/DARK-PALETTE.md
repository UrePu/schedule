## 2. 구현 방식과 이유

### 2-1. 토큰만 바꾼다 — 컴포넌트에 `dark:` 가 **하나도 없다**

유틸리티(`bg-surface`, `text-ink`)는 전부 `var(--color-*)` 를 참조하므로 **변수 값만
갈아끼우면 전 화면이 따라온다.** 컴포넌트마다 `dark:` 를 달면 새 컴포넌트가 생길 때마다
빠뜨리게 되고, 어떤 조합이 검증됐는지 아무도 모르게 된다.

이 원칙 때문에 **겹침 농도 표현을 알파에서 의미 토큰으로 승격**했다:

```
이전: bg-primary/25 → /45 → /70 → primary   (흰 배경 기준으로 고른 알파)
이후: bg-overlap-1 → -2 → -3 → -4           (테마가 값을 정한다)
```

같은 이유로 `bg-available`, `bg-excluded`, `bg-scrim` 도 토큰이 되었다.

### 2-2. `@theme` 밖에서 변수를 재정의한다

Tailwind v4 의 `@theme` 는 유틸리티 생성을 위한 정적 선언이라 미디어 쿼리를 넣을 수 없다.
그래서 다크 값은 **일반 CSS 규칙에서 같은 변수를 덮어쓴다.** `@theme` 는 `@layer theme`
안으로 들어가고 다크 규칙은 레이어 밖이라 항상 이긴다.

### 2-3. 적용 경로가 둘, 값은 한 곳

```css
:root { --dk-surface: #18181d; /* … 값은 여기 한 번만 */ }

@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) { --color-surface: var(--dk-surface); /* … */ }
}
:root[data-theme="dark"]          { --color-surface: var(--dk-surface); /* … */ }
```

- **기본은 `prefers-color-scheme`** — 아무것도 안 고르면 OS 를 따른다.
- **명시 선택은 `data-theme`** — `localStorage("m-schedule.theme")` 에 저장된다.
- 두 적용 규칙이 필요하지만 **색 값 자체는 `--dk-*` 에 한 번만** 적어 갈라지지 않게 했다.
- `:not([data-theme="light"])` 가 있어서, OS 가 다크여도 사용자가 라이트를 고르면 라이트가 이긴다.

### 2-4. FOUC 방지

`<head>` 안 인라인 스크립트가 **첫 페인트 전에** `data-theme` 를 확정한다
(`src/lib/theme.ts` 의 `THEME_INIT_SCRIPT`). 하이드레이션 후에 적용하면 라이트가 한 번
번쩍인 뒤 다크로 바뀐다. 저장값이 없으면 아무것도 하지 않고 CSS 의 미디어 쿼리에 맡긴다.

`<html>` 에 `suppressHydrationWarning` 을 둔 이유도 이것이다 — 스크립트가 서버 HTML 의
속성을 바꾸기 때문이며, 의도된 차이다.

### 2-5. 토글 위치

레이아웃의 얇은 상단 바에 두었다. `/`, `/schedule`, `/showcase` 전부에서 접근된다.
상태는 3단계(**시스템 / 라이트 / 다크**)다 — 라이트·다크 2단계만 두면 "OS 를 따라가라"를
표현할 수 없어, OS 를 다크로 바꿔도 앱이 따라가지 않는다.

선택값은 React 밖(localStorage)에 있으므로 `useSyncExternalStore` 로 읽는다.
`useState` + `useEffect` 로 하면 effect 안 setState 가 생기고 첫 렌더가 한 프레임 어긋난다.

## 4. 겹침 농도 램프 — 다크용으로 **다시 산정**

> ⚠️ **이 절의 값은 §6-5(2026-09-03)가 대체했다.** 램프는 4단 → **5단**이 되었고
> 라이트·다크 값이 전부 바뀌었으며, 판정 기준도 비율에서 **인원수**로 바뀌었다.
> 이 절은 왜 다크를 따로 산정해야 하는지(원칙)와 당시 기록으로만 남긴다 —
> 현행 값은 §6-5 를 보라.

라이트의 알파(22/45/72%)를 어두운 바탕에 그대로 쓰면 네 단계가 뭉개진다.
다크는 primary 를 surface 에 **26/50/74%** 로 섞었다 (OKLab 혼합).

| 단계 | 라이트 | 상대휘도 | 다크 | 상대휘도 |
|---|---|---|---|---|
| `overlap-1` | `#d2d9fe` | 70.48 | `#32324e` | 3.51 |

**네 단계가 실제로 구분되는가** — 인접 단계 간 대비비:

| 인접 쌍 | 라이트 | 다크 |

## 6. 타이포그래피 — 한글 폰트

### 문제

`Outfit`(제목) + `Inter`(본문) 은 **둘 다 한글 글리프가 없다.** 화면의 거의 전부가
한국어인 앱에서 모든 한글이 OS 기본 폰트(맑은 고딕 / Apple SD Gothic)로 떨어졌다.

- 머신마다 다르게 보여 디자인 검수가 성립하지 않는다
- 한 줄에 한글+영문이 섞이면 **서로 다른 두 폰트가 이어 붙어** 자소 크기·굵기·베이스라인이 어긋난다
  (이 앱은 `카오스 칼로스 · Lv.295 · 21:00` 같은 줄이 계속 나온다)
- 숫자가 어느 폰트에서 나오는지 불확실해 표 정렬이 흔들린다

  preload 를 켜면 `<link rel=preload>` 가 쏟아져 오히려 초기 로딩을 방해한다.
  대신 `display: "swap"` + next/font 자동 폴백 크기 보정으로 레이아웃 흔들림을 줄인다.

## 6-2. 유동 타입 스케일 — 뷰포트 **너비**에 반응

발주 요구: *"모든 글씨 w 에 따라 바꾸고"* → 뷰포트 **너비(width)** 에 따라 타이포가 유동적으로
변해야 한다는 뜻으로 해석했다. 구현은 `src/app/globals.css` 의 `@theme` 토큰뿐이며,
**컴포넌트에는 크기 분기가 한 줄도 없다** (다크 모드와 같은 원칙 — §2-1).

### 방식

```css
--text-subhead: clamp(20px, 17.652px + 0.6522vw, 26px);
/*                 ↑하한        ↑선형보간         ↑원본 디자인 값(상한) */
```

- 보간 구간은 **360px → 1280px**. 360px 은 실사용 최소 폭, 1280px 은 본문 컨테이너가
  `max-w-6xl`(1152px)에서 이미 멈추는 지점이라 그 이상은 레이아웃이 넓어지지 않는다.
- **상한 = 기존 디자인 값 그대로.** 디자인이 바뀌는 것이 아니라 좁은 화면에서 줄었다가
  데스크톱에서 원래 값으로 돌아오는 것이다. 1280px 을 넘어도 더 커지지 않는다.
- 단위는 기존과 같이 **px + vw**. rem 으로 바꾸면 루트 폰트 크기가 16px 이 아닌 환경에서
  모든 값이 달라져 "데스크톱 상단값 = 현재값" 제약이 깨진다. 브라우저 확대는 `vw` 도
  함께 확대하므로 확대 경로의 가독성은 유지된다.

### 작은 것은 줄이지 않는다 (§4 가독성 규칙)

**문장은 어떤 폭에서도 14px 미만으로 내려가지 않는다.** 그 결과 하한 = 상한이 되는 토큰은
`clamp` 를 쓰지 않고 상수로 둔다 — 두 제약(“더 작아지면 안 된다” + “원본값을 넘을 수 없다”)이
만나면 답은 상수 하나뿐이다.

| 토큰 | 360px | 768px | 1280px 이상 | 비고 |
|---|---|---|---|---|
| `display` | 32.00 | 40.87 | **52.00** | 52px 이 모바일에 그대로면 화면을 뚫는다 |
| `headline` | 26.00 | 31.32 | **38.00** | |
| `subhead` | 20.00 | 22.66 | **26.00** | |
| `body-lg` | 16.00 | 16.89 | **18.00** | 하한 16px — `body-sm` 과 붙어 위계가 무너지지 않게 |
| `body` | 14.00 | 14.44 | **15.00** | 하한 = 문장 하한 14px |
| `body-sm` | 14.00 | 14.00 | 14.00 | **문장 하한. 상수.** |
| `label` | 13.00 | 13.00 | 13.00 | 폼 라벨·필터 칩 전용. 상수 |
| `caption` | 12.00 | 12.00 | 12.00 | 배지·타임스탬프 전용. 상수 |
| `overline` | 11.00 | 11.00 | 11.00 | 스케일 최하단. 상수 |
| `code` | 14.00 | 14.00 | 14.00 | API 키·ocid. 상수 |

> 문장 계열 최솟값 = **14px** (모든 폭에서). 320px 같은 극단 폭에서도 clamp 하한이 지킨다.

### 행간·자간은 손대지 않았다

둘 다 **무단위(line-height)** 또는 **`em`(letter-spacing)** 이라 글자 크기에 **비례해 함께
줄어든다.** 헤딩 행간을 1.1→1.2 등으로 올린 근거(한글 글자틀이 라틴보다 커서 상대적 여백이
부족하다)도 크기에 비례하는 성질이므로, 비례 유지가 그대로 정답이다. 자간도 전 구간
양수(0.01~0.09em)라 축소 구간에서 글자가 붙을 위험이 없다. px 로 고정했다면 32px 제목에
52px 기준 여백이 남아 반대로 깨졌을 것이다.

### 대비 회귀 없음

크기는 WCAG 대비비를 바꾸지 않는다. 다만 **임계값**은 바꾼다 — 24px 미만으로 내려간 헤딩은
"큰 텍스트(3:1)"가 아니라 본문(4.5:1) 기준을 받는다. 축소되는 헤딩이 쓰는 색 조합은 전부
그 기준을 통과한다:

| 조합 | 라이트 | 다크 |
|---|---|---|
| 헤딩 `ink` / `background` | 16.97:1 | 17.27:1 |
| 헤딩 `ink` / `surface` | 17.72:1 | 16.09:1 |
| 오버라인 `primary` / `background` | 6.02:1 | 6.12:1 |

최근 FAIL→PASS 로 고친 6곳도 그대로다(색 조합을 건드리지 않았다):
`ink-muted/surface` 4.83·9.01 · `ink-label/neutral-100` 9.50·10.83 ·
`ink-label/hover-surface` 9.50·10.57 · `ink/chip-soon-bg` 16.69·14.12 (라이트·다크 순).

## 6-3. 보스 난이도 — **전용 램프로 분리**하고 라이트 대비를 고쳤다

### 무엇이 문제였나

난이도는 브랜드 토큰(`neutral-400`/`secondary`/`primary`/`warning`/`tertiary`)을 **빌려 쓰고
있었다.** 두 가지가 동시에 잘못이었다.

1. **의미 축이 다르다.** 브랜드 색을 조정하면 난이도 위계가 같이 흔들린다. 난이도는 브랜드가
   아니라 **도메인 척도**다.
2. **라이트 모드에서 사실상 구분되지 않았다.** 5단계 중 4개가 UI 경계 기준 3:1 미달이었고,
   그 4개는 서로 **명도가 거의 같았다.**

| 난이도 | 옛 라이트 | vs `surface` | 옛 다크 | vs `surface` |
|---|---|---|---|---|
| easy | `#a1a1aa` | 2.56 ✗ | `#6b6b76` | 3.36 ✓ |
| normal | `#06b6d4` | 2.43 ✗ | `#3fd3ec` | 9.89 ✓ |
| hard | `#4f46e5` | 6.29 ✓ | `#8b85f5` | 5.70 ✓ |
| chaos | `#f59e0b` | 2.15 ✗ | `#fbbf24` | 10.60 ✓ |
| extreme | `#f97316` | 2.80 ✗ | `#fb923c` | 7.82 ✓ |

옛 인접 쌍(정상 시각): 라이트 **1.06 / 2.59 / 2.93 / 1.31**, 다크 **2.94 / 1.73 / 1.86 / 1.36**.
숫자가 오르내린다는 것은 **명도가 난이도 순서를 전혀 나타내지 못했다**는 뜻이다.
가장 약한 쌍 chaos↔extreme 은 색상각으로만 갈려 색각 이상 사용자에게는 같은 색이었다
(deutan 시뮬레이션 라이트 **1.24**, 다크 **1.30**).

### 설계 원칙 — 난이도는 **순서가 있는 척도**다

이지 < 노멀 < 하드 < 카오스 < 익스트림. 그래서 **명도가 그 순서를 따라 단조롭게 변하도록**
잡았다. 색상 정보를 완전히 제거해도 순서가 읽히면 색각 이상 대응이 자동으로 따라온다.

- **라이트는 어려울수록 어두워지고, 다크는 어려울수록 밝아진다.** 방향은 반대지만 의미는
  같다 — 양쪽 다 *"어려울수록 표면 대비가 커진다"*. §1 의 "다크는 반전이 아니다" 원칙과 같은
  논리다(면이 올라갈수록 밝아지는 것과 동형).
- **색상 정체성은 유지한다**: 무채색 → 청록 → 남색 → 호박 → 주황.
- **익스트림은 red 가 아니다.** §4 가 red 를 실패·취소 전용으로 못 박았다.
- 값은 OKLCH 에서 **색상(hue)을 고정한 채 명도만 이분 탐색**해 목표 WCAG 상대휘도에 맞췄다.
  채도는 그 명도에서 sRGB 가 허용하는 최대치의 82%(라이트)·90%(다크)로 두었다 — 감마 끝단에
  붙은 형광색을 피하기 위해서다.

### 램프가 **두 벌**인 이유 — 요구 대비가 다르다

| 램프 | 쓰는 곳 | 기준 | 최적화 대상 |
|---|---|---|---|
| `difficulty-*` | `border-l-*` `border-*` `bg-*` | WCAG 1.4.11 **3:1** | **인접 단계 명도차** (역할 = 구분) |
| `difficulty-*-ink` | `text-*` | 본문 **4.5:1** | **가독성** (역할 = 읽힘) |

난이도 오버라인은 11px/700 이라 WCAG 의 "큰 텍스트"(18.66px bold)에 못 미쳐 3:1 이 아니라
**4.5:1** 을 받는다. 그래서 면 램프를 글자에 그대로 쓰면 안 된다 — `ink-placeholder` 와 같은
함정이다(§4 가독성 규칙).

> **한 램프로 합치는 안을 실제로 계산해 보고 버렸다.** 전 구간을 4.5:1 에 앵커하면 램프의
> 아래쪽이 밀려 올라가는 만큼 위쪽 여유가 사라진다. 다크에서 인접 쌍이 **1.03:1**(tritan
> 이지↔노멀)까지 무너져, 원래 고치려던 "구분이 안 된다"가 그대로 재발했다.
> 역할이 다르면 램프도 달라야 한다.

서버·클라이언트 양쪽에서 import 된다. export: `BOSS_DIFFICULTIES` · `BossDifficulty` ·
`BOSS_DIFFICULTY_LABEL` · `BOSS_DIFFICULTY_BORDER_L`(`border-l-*`) ·

  `` `border-${x}` `` 같은 런타임 조합은 빌드 결과에서 사라진다.
- 주간 숙제는 보스가 아니므로 계속 **무채색 `neutral-300`** 을 쓴다(난이도 램프 밖).

> ⚠️ 4.2MB 는 **디스크 산출물 총량**이지 페이지당 전송량이 아니다. `unicode-range` 로

> 추정된다. **실측은 브라우저 개발자 도구가 필요하며 이번 검증에서는 하지 못했다.**

## 6-4. 라이트 모드 대비 감사 — **미달 140건 → 0건** (2026-08-19)

> 감사 도구: `pnpm contrast` (`scripts/contrast-audit/`). 이 절의 모든 수치는 그 도구의 출력이다.
> 원본 `pipelinepro-DESIGN.md` 는 이번에도 **수정하지 않았다.** 라이트 값 조정 근거는 전부 여기 있다.

### 왜 라이트만 문제였나

다크 팔레트는 §5 에서 실측을 거쳐 만들어졌다. **라이트는 원본 디자인 문서 값을 그대로 쓰고
한 번도 재산정되지 않았다.** 그래서 다크만 보면 전부 통과하고, 라이트에서만 무너지는
조합이 **140건**(글자 86 + 아이콘 54) 쌓여 있었다. 그중 16건은 WCAG·§4 면제로 재분류했고
**124건은 실제로 고쳤다.** §4 가 "두 테마 모두 실제 색 쌍으로 계산하라"고 못 박은
이유가 정확히 이것이고, 이번에는 **라이트가 더 나쁜 쪽**이었다.

가장 아픈 하나: **메소 금액**(`MesoAmount tone="accent"`, 13곳)이 `background` 위 **2.33:1**.
이 앱에서 가장 중요한 숫자가 가장 안 읽히는 색이었다.

### 감사 도구가 하는 일 — 토큰 표가 아니라 **화면에서 만나는 쌍**을 본다

과거 사고(§3 의 다크 `ink-muted`)는 "`surface` 하나만 놓고 검사해 통과 판정"이었다.
그 실수를 도구로 막는다.

1. `src/app/globals.css` 에서 라이트·다크 색 토큰과 타이포 토큰을 **직접 읽는다**
   (손으로 옮겨 적은 표가 없다 — 감사기와 브라우저가 같은 파일을 본다).
2. `src/**` 의 JSX 트리를 TypeScript AST 로 걸으며 **조상의 배경**을 물려받아 전경색과 짝짓는다.
   `hover:` 로 바뀌는 면도 같은 글자가 실제로 앉는 면이므로 후보에 넣는다.
3. 데카르트 곱을 만들지 않기 위해 두 장치를 둔다.
   - **분기 전개**: `cn(sel ? "bg-primary text-surface" : "bg-surface text-ink-label")` 을
     배타적 조합으로 펼친다. 안 그러면 `text-surface / bg-surface`(1.0:1) 같은 유령이 생긴다.
   - **분기 상관(Guard)**: 부모의 `checked ? A : B` 와 자식의 `checked ? C : D` 를 **같은 조건**으로
     묶는다. 이걸 넣기 전에는 `text-primary / hover-strong`(다크 4.27:1)이라는 없는 미달이 나왔다.
4. 알파(`text-ink/50`, `bg-primary/25`)는 **sRGB 감마 공간에서 합성한 뒤** 계산한다.
5. 판정할 수 없는 것(임의값 클래스, 형제 위에 얹힌 절대 위치 요소)은 **"수동 확인 필요"로 출력**한다.
   조용히 건너뛰지 않는다.

임계값: 본문 4.5:1 · 큰 텍스트(24px+ 또는 18.66px+ 700) 3:1 · 장식/UI 경계 3:1.
글자 크기는 유동 스케일(§6-2)의 **하한(모바일)** 으로 판정한다 — 가장 불리한 쪽이 실제로 존재한다.

- **형제 위에 얹힌 절대 위치 요소 5건** — 체크박스의 체크 표식처럼 배경을 지는 것이 조상이 아니라
  `peer` 형제인 경우. 조상 면으로 계산하면 틀린 값이 나오므로 판정하지 않고 목록으로 낸다.
- **`className` 이 식별자/맵 조회인 경우** — 값을 알 수 없다. 그런 문자열은 별도 경로로 모아
  "흔한 면 전부"(background·surface·hover-surface·neutral-100)에 대해 검사한다.
  `MesoAmount` 의 `accent` 를 잡아낸 것이 정확히 이 경로다.
- **육안 검수는 여전히 못 했다**(§7). 전부 계산이다.

### 14px 미만 문장 규칙 (§4) — 발견 29건, 이번에는 **고치지 않았다**

`pnpm contrast` 가 함께 출력한다. 대부분은 문장이 아니라 **수치 라벨 줄**
(`주간 보스 6개 · 남은 2개`, `예상 수령액 · 3인 분배`)이라 12px 이 §4 가 허용한 "수치 주석"에
해당한다. 검출기가 자식 노드를 이어 붙여 보여 주는 탓에 문장처럼 보일 뿐이다.
실제로 문장인 것은 `showcase` 페이지 3건 정도이며, 그중 각주 한 줄은 이번에 14px 로 올렸다.
나머지는 색 대비와 별개 사안이라 이번 범위에서 제외했다 — **판단 근거가 되도록 목록은 계속 출력된다.**

## 6-5. 겹침 농도 램프 — **4단 → 5단**, 비율이 아니라 인원수 (2026-09-03)

### 무엇이 문제였나

발주 지시 두 개가 같은 화면을 가리켰다.

> *"겹침을 색마다 다르게 하여 2명이상 겹치는 부분을 투명도 차이나 색 차이로 보이게 해줘
> 누가봐도 아 이게 더 많이 겹치는군 할수있는 색으로"*

세 가지가 겹쳐 있었다.

1. **1단이 사실상 보이지 않았다.** 옛 `overlap-1 #d2d9fe` 는 흰 면(`surface`) 대비
   **1.19:1**, 밴드 트랙(`neutral-100`) 대비 **1.08:1**. §4 는 UI 경계에 3:1 을 요구한다.
2. **판정이 비율이었다.** `count / total` 로 4단을 탔기 때문에 6인 파티의 2명은
   `0.33` → 1단(안 보이는 그 색)이었고, 무엇보다 최소 인원 기본값이 `전원` 이라
   **모든 겹침 창의 비율이 1.0**, 즉 화면 전체가 한 색이었다.
3. **4단으로는 6인 파티를 못 가른다.** 2·3·4·5·6명 다섯 가지를 네 색에 넣으면
   반드시 두 인원이 한 색을 쓴다.

### 인원수 → 단계 매핑

| 겹침 인원 | 단계 | 근거 |
|---|---|---|
| 2명 | `overlap-1` | 겹침 창의 하한(1명은 겹침이 아니다) |
| 3명 | `overlap-2` | |
| 4명 | `overlap-3` | |
| 5명 | `overlap-4` | |
| 6명 이상 | `overlap-5` | 최대 파티가 6인이라 사다리는 여기서 멈춘다 |
| **`count === total`(전원)** | **`overlap-5`** | 인원수와 무관하게 최고 단 |

마지막 줄이 규칙의 핵심이다. **3인 파티의 3명은 6인 파티의 6명과 같은 뜻**("더 부를
사람이 없다")이고 그것이 이 화면에서 가장 좋은 소식인데, 절대 인원수만 보면 작은 파티는
최고 단에 영영 닿지 못한다. 반대로 비율만 보면 6인 파티의 2명과 3인 파티의 1명이 같은
색이 되어 "몇 명이 겹치나"라는 질문에 답하지 못한다. 그래서 **기본은 절대 인원수, 전원만
예외**다.

### 팔레트 유도 — 두 제약이 값을 거의 다 정한다

색상각은 primary 계열(HSL 245°) 그대로 두고, **명도**로 다섯 단을 만들되 채도를 함께
움직여(라이트 92→68%, 다크 36→80%) 단계 간 인상 차이를 벌렸다. 명도를 정한 것은 두 제약이다.

1. **1단은 밴드 트랙 대비 3:1 이상**(§4, UI 경계). 트랙은 `surface` 가 아니라
   `neutral-100` 이므로 흰 면 기준으로는 3.30:1 이 실질 하한이다 — §4 가 못 박은
   *"토큰 표가 아니라 렌더된 짝으로 판정한다"* 를 그대로 적용한 값이다.
2. **각 단 위 글자는 4.5:1 이상.** 밴드 라벨은 14px bold(가로) · 11px bold(세로)라
   WCAG 의 "큰 텍스트"에 못 미쳐 4.5:1 을 받는다.

⚠️ 두 번째 제약에 **함정**이 있다. 어떤 면에 대해 `잉크 대비 × 흰색 대비` 는 상수다
(라이트 **17.7**, 다크 **17.27**). 그래서 흰 면 대비가 **3.93 ~ 4.5 사이인 색은 잉크도
흰색도 4.5:1 을 못 넘긴다** — 어떤 전경색을 골라도 AA 미달인 죽은 구간이다. 1단은 제약 1
때문에 3.30 이상이어야 하고 제약 2 때문에 3.93 이하여야 하므로 **[3.30, 3.93] 안에**
있어야 하며, 2단은 그 죽은 구간을 건너뛰어 4.5 이상에서 시작해야 한다. 전경색이 1→2 에서
한 번 뒤집히는 것은 취향이 아니라 이 산술의 결과다. (다크도 방향만 반대일 뿐 같다.)

남은 자유도는 사다리의 위쪽 끝뿐이다. 라이트는 옛 최고단 `primary #4f46e5`(6.29:1)보다
더 내려 **12.53:1** 까지 갔다 — 그래야 네 칸을 1.37~1.39:1 로 고르게 벌릴 수 있고,
난이도 램프(§6-3)가 1.31~1.32:1 로 다섯 단을 구분해 낸 것과 같은 폭이 된다.

### 색이 유일한 채널이 아니다 (§4)

- 밴드 안에 **인원수를 숫자로** 찍는다. 라벨 임계값을 가로 3% → **1.5%**(≈10px),
  세로 6% → **4%**(≈10px)로 내려 자리가 있는 한 언제나 나오게 했다. 그보다 얇은 막대는
  글자 조각만 보여 오히려 못 읽으므로 비우고, 그때도 `aria-label`·`title` 이 인원수를 말한다.
- 세로 격자의 겹침 막대에는 `aria-label` 이 아예 없어 읽어 주기에 숫자 하나(`3`)만
  도달했다 — 인원인지 순번인지 알 수 없었다. 가로 격자에는 진작 있던 것이라
  §0.2(같은 결함은 형제 화면에도 있다)에 따라 이번에 함께 넣었다.
- 범례가 다섯 단을 **인원 라벨과 함께** 늘어놓는다. 옛 범례는 `전원 / 다수 / 최소 k명`
  세 칸이라 "다수"가 몇 명인지 말하지 않았다.

### 축 잘림 표식 — 왜 겹침 램프 밖의 색을 썼는가

같은 작업에서 시간축을 **겹침 앞뒤 2시간**으로 좁히는 토글이 들어갔다(기본값 `겹침 주변`).
좁힌 축은 개인 막대·잡힌 일정을 잘라 낼 수 있어, 잘린 레인 끝에 이어짐 표식을 그린다.

표식 색은 `bg-ink` + `ring-1 ring-surface` 다. **겹침 램프 안의 색을 쓰면 반드시 어느 한
단에서 묻힌다** — 예컨대 `ink` 는 라이트 `overlap-1` 위에서 5.13:1 이지만 `overlap-5`
위에서는 1.41:1 이다. 링이 반대쪽 후광(라이트 흰색 / 다크 근-검정)을 만들어, 다섯 단 중
어디에 얹혀도 **안쪽과 링 중 한쪽은 반드시 진하게 갈린다**:

| 얹히는 면 | 안쪽 `ink` | 링 `surface` |
|---|---|---|
| 라이트 `overlap-1` | 5.13:1 | 3.45:1 |
| 라이트 `overlap-5` | 1.41:1 | **12.53:1** |
| 다크 `overlap-1` | 4.76:1 | 3.38:1 |
| 다크 `overlap-5` | 1.57:1 | **10.24:1** |

플레이헤드가 `bg-playhead ring-playhead-edge` 로 쓰는 방법과 같은 원리다.
색만으로 말하지 않도록 각 표식은 `sr-only` 문장을 함께 들고 있고, 범례에도 항목이 있다
(축을 좁혔을 때만 — 표식이 없는 화면에 설명을 두면 있지도 않은 것을 찾게 만든다).

### 회귀 검사

`pnpm contrast` 결과가 **변경 전후 완전히 동일**했다(라이트 글자 7건 · 다크 1건 미달,
장식 0건 — 전부 이번 작업과 무관한 기존 항목). 수집 조합만 838 → 845 건, 색 토큰
64 → 66 개로 늘었다. 겹침 램프 자체는 `overlapToneClass()` 가 클래스를 함수로 반환해
스캐너가 짝을 잡지 못하므로, 위 표들은 `--pair` 로 직접 측정한 값이다.

## 7. 확인하지 못한 것

- **육안 검수를 하지 못했다.** 이 환경에는 브라우저 자동화 도구가 없다.
  대비·명도는 전부 계산으로 검증했고, 생성 CSS 에 다크 토큰이 방출되는 것과
  적용 규칙 두 벌이 존재하는 것은 확인했지만, **실제 픽셀을 본 것은 아니다.**
- **페이지당 폰트 전송량 실측** — 위와 같은 이유.
- 라이트 상태 칩·`border-strong` 의 대비 미달은 **원본 디자인 문서 값**이라 손대지 않았다.
  고칠지 여부는 발주 판단이 필요하다.

겹쳐보기에서 **고른 시작 시각**을 가리키는 선과 손잡이. 발주 지시: *"보라색의 반대가

| | 라이트 | 다크 |
|---|---|---|
| `--color-playhead` | `#facc15` | `#fde047` |
| `--color-playhead-edge` | `#18181b` | `#18181b` (같은 값) |

**유도 근거**

- primary `#4f46e5` 는 HSL 색상환에서 **243°**. 그 보색은 **63° = 노랑**이다.
- tertiary orange 를 쓸 수 없다 — 같은 격자에서 **예외(특이사항)** 구간이 이미 쓰고 있다
  (`--color-excluded`). red 도 안 된다(실패·취소 전용, §4). 노랑은 이 격자에서 아직
  아무 뜻도 없는 색이고, 마침 primary 의 보색이라 겹침 밴드 위에서 가장 멀리 떨어진다.
- **테두리만 두 테마가 같다.** 노랑은 라이트·다크 어디서나 밝은 색이라, 표면색 링을
  두르면 라이트에서 흰 위 노랑 = **1.6:1** 로 사라진다. 고정된 어두운 테두리 하나가 두
  테마를 함께 해결한다(영상 편집기의 빨간 재생 헤드도 같은 이유로 어두운 획을 두른다).
- 대비: `#facc15` on `#18181b` = **11.9:1** · `#fde047` on `#09090b` = **15.4:1**.
  글자(시각 라벨)는 `playhead` 바탕에 `playhead-edge` 글자라 같은 값이 적용된다.
- 다크가 한 단계 밝은 이유: 이 선은 다크 겹침 밴드(`#32324e`~`#4f46e5`) 위를 지나므로
  그보다 확실히 밝아야 "선이 밴드 위를 지나간다"가 읽힌다.
