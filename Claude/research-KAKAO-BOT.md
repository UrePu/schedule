# 카카오톡 오픈채팅방 봇 연동 조사 (research-KAKAO-BOT)

> 조사일: 2026-08-17 · 대상: M_Schedule 카카오 알리미 (CLAUDE.md §1 도메인, §2 기술결정 기준)
> 요구사항: **카카오톡 계정 하나를 봇으로 만들어 방에 넣어두고, 방에서 `!경험치` 같은 명령어를 치면 봇이 대답한다.**
> 즉 **명령어 → 응답(pull)이 주(主)**, 선제 푸시 알림이 부(副).
> 모든 결론에는 §출처의 URL이 대응한다. 확인하지 못한 항목은 **미확인**으로 명시했다.

## 결론 요약

**오픈채팅방은 카카오 공식 API의 지원 대상이 아니다. 따라서 요구사항은 "카카오톡 계정으로 로그인한 단말에서 도는 비공식 봇 런너"로만 구현 가능하며, 우리 서버는 그 런너와 HTTP 한 번으로 끝나는 얇은 계약만 갖는다.**

공식 경로 조사 결과를 한 문단으로 압축하면 이렇다. 카카오 데브톡에서 "디스코드/텔레그램/슬랙처럼 그룹채팅에 챗봇을 붙이는 webhook API"를 요청한 질문에 카카오 운영자가 **"아쉽지만, 디벨로퍼스에서는 오픈채팅 관련 API를 제공하지 않습니다"** 라고 답했고 [1], 다른 문의에서도 계정탈취·피싱·스팸·수신동의 문제를 사유로 미제공을 확인하며 대안으로 카카오톡 **채널** 1:1 채팅을 안내했다 [2]. 챗봇 관리자센터(구 카카오 i 오픈빌더) 공식 문서 역시 "제작한 챗봇은 **카카오톡 채널**과 연결하여 서비스를 제공한다"고만 명시하며 오픈채팅방은 연결 대상에 없다 [3]. 카카오톡 메시지 API는 수신 대상이 *나와의 채팅방*(나에게 보내기) 또는 *같은 서비스에 카카오 로그인한 사용자*(친구에게 보내기)로 한정되고 오픈채팅방 발송 서술이 전혀 없다 [4]. 알림톡·친구톡은 비즈니스 채널 전환·홈공개·고객센터 정보·발신프로필 키·템플릿 심사·공식 딜러사 경유가 요건이며 수신 대상은 전화번호 기반 개인이라 목적지 자체가 다르다 [5][6]. 카카오가 오픈채팅에 제공하는 유일한 내장 봇인 **방장봇**은 환영 메시지 / 정시 알림 / 키워드 Q&A 최대 10개를 지원하지만 방장이 UI에서 고정 문구를 등록하는 노코드 기능이고 **외부 서버 연동 수단이 없어** "이번 주 결정석 미수령 3개" 같은 계산된 값을 넣을 수 없다 [7][8]. → **공식 경로 전부 불가. 이하는 비공식 봇 런너 전제로 서술한다.**

정리하면 구현 구조는 다음 한 줄이다.

```
[오픈채팅방] --(!명령어)--> [봇 계정 단말의 런너] --HTTP--> [우리 서버] --{"reply":"..."}--> [런너] --> [방에 평문 답장]
```

우리 서버가 하는 일은 **JSON 하나 받아서 문자열 하나 돌려주는 것**이 전부다. 카카오톡을 아는 코드는 서버에 단 한 줄도 두지 않는다 (CLAUDE.md §2 "우리 서버는 표준 웹훅 어댑터만 제공" 그대로).

## 1. 봇 런너 — 실동작 사양

봇 런너는 두 계열로 갈린다. **런너를 무엇으로 고르든 우리 서버 인터페이스는 §3 하나로 고정**이며, 아래는 그 인터페이스를 만족시키기 위해 런너 쪽에서 무엇을 해야 하는지를 실제 사양 기준으로 정리한 것이다.

### 1.1 계열 A — 알림 리스너 방식 (메신저봇R / Messenger Bot R)

**동작 원리.** 안드로이드의 `NotificationListenerService`로 `com.kakao.talk`이 올리는 알림을 가로채 방 이름·발신자·메시지를 뽑아내고, Rhino JavaScript 엔진으로 사용자 스크립트를 실행한다. 답장은 알림에 붙어 있는 **다이렉트 리플라이 액션**을 눌러 보낸다 [12][13][19].

**진입점 시그니처 — 레거시 API (API1)** [12][18]

```js
function response(room, msg, sender, isGroupChat, replier, imageDB, packageName) { ... }
```

| 인자 | 의미 |
|---|---|
| `room` | 메시지가 온 채팅방 **이름 문자열** (← 안정적 ID가 아님. §3.4 참조) |
| `msg` | 메시지 내용 |
| `sender` | 보낸 사람 **닉네임 문자열** (← 안정적 ID가 아님) |
| `isGroupChat` | 단체톡이면 `true` |
| `replier` | 답장 객체. `replier.reply(msg)` = 온 방에 답장, `replier.reply(room, msg, hideToast)` = 지정한 방에 답장 |
| `imageDB` | 프로필 이미지 |
| `packageName` | `com.kakao.talk` |

**진입점 시그니처 — API2 (현행)** [16][17][18]

```js
const bot = BotManager.getCurrentBot();
bot.addListener(Event.MESSAGE, (chat) => { ... });   // bot.on(...) 도 동일
```

`chat` 객체 필드 [17]:

| 필드 | 타입 | 의미 |
|---|---|---|
| `chat.room` | String | 채팅방 방제 |
| `chat.content` | String | 메시지 내용 |
| `chat.author.name` | String | 전송자 이름 |
| `chat.author.avatar` | Object | 프로필 이미지 (`getBase64()` / `getBitmap()`) |
| `chat.isGroupChat` | Boolean | 단체톡 여부 |
| `chat.isDebugRoom` | Boolean | 디버그룸 메시지 여부 |
| `chat.isMention` | Boolean | 멘션 포함 여부 |
| `chat.packageName` | String | 메신저 앱 패키지명 |
| `chat.reply(content)` | Method | 답장 전송 |
| `chat.markAsRead()` | Method | 읽음 처리 |

Bot 인스턴스 메서드 [16][18]:

| 메서드 | 용도 |
|---|---|
| `bot.send(room, msg[, packageName])` | **지정한 방에 능동 전송** (푸시 알림용 — §3.3) |
| `bot.canReply(room[, packageName])` | 해당 방에 전송 가능한지 사전 확인 |
| `bot.setCommandPrefix(prefix)` | 커맨드 접두어 설정 (우리는 `!`) |

**외부 HTTP 호출 방식.** Rhino가 Java 클래스에 직접 접근하므로 `org.jsoup.Jsoup.connect(url)` 체인으로 GET/POST를 보낸다. 레거시 헬퍼로 `Utils.getWebText(url)`(내부적으로 Jsoup GET), `Api.parse(url)`(Document 반환)이 있다 [13][20]. 즉 **POST + JSON 본문 + 커스텀 헤더 전송이 가능**하다.

**계열 A의 치명적 제약 — 발주자가 알아야 할 것** [12][21]

| 제약 | 내용 |
|---|---|
| 알림이 안 뜨면 봇도 안 돈다 | **해당 채팅방 화면에 들어가 있으면 알림이 안 떠서 봇이 반응하지 않는다** [21]. 봇 계정을 사람이 쓰던 폰에서 돌리면 안 되는 이유다. |
| 알림 내용 숨김 금지 | 알림 미리보기를 끄면 런너가 내용을 못 읽는다 [21] |
| 배터리 최적화 제외 필수 | 앱 강제 종료·메모리 정리 후 카톡 재실행 전까지 알림이 안 뜬다 [21] |
| **도배 방지** | **직전과 동일한 내용을 연속 전송하면 카톡이 막는다.** 런너 설정에서 비활성화 가능 [21]. 우리 응답이 매번 같은 문자열이면 두 번째부터 안 나갈 수 있다 → §3.5 대응 |
| 버전 취약성 | 안드로이드/카카오톡 버전마다 알림 구조가 달라 파싱이 깨진다. **카톡 앱이 업데이트될 때마다 봇이 죽을 수 있다** [12][13] |

### 1.2 계열 B — DB 관찰 방식 (Iris / PyKakaoDBBot)

**동작 원리.** 루트 권한으로 카카오톡의 내부 SQLite DB를 폴링해 신규 행을 감지하고, 암호화된 메시지를 복호화해 외부로 넘긴다. 전송은 시스템 서비스를 통해 방 ID로 직접 보낸다. **알림에 의존하지 않으므로 계열 A의 제약(화면 켜짐, 방 진입 중, 알림 숨김)이 전부 사라진다** [14].

**구동 요건** [14][15]

- 카카오톡이 설치된 안드로이드 기기 + **루트 권한** (DB 접근용)
- 또는 **Redroid 도커 컨테이너**(Android 11, `--privileged`)로 서버에서 구동 — 물리 폰 없이 리눅스 서버 하나로 끝낼 수 있다 [15]
- Iris는 APK를 adb로 설치 후 `iris_control start`, `http://[ANDROID_IP]:3000/dashboard`에서 설정 [14]

**우리 서버와의 연결 — 두 가지 모드** [14]

1. **Iris가 직접 우리 서버를 호출 (endpoint 모드)** — `POST /config/endpoint` 에 `{"endpoint": "https://.../..."}` 를 설정하면, 신규 메시지 감지 시 Iris가 그 주소로 POST한다. 보내는 페이로드는 Iris가 정한 고정 형태다:

   ```json
   {
     "msg": "[복호화된 메시지]",
     "room": "[채팅방 이름]",
     "sender": "[발신자 이름]",
     "json": { "_id": "...", "message": "...", "attachment": "..." }
   }
   ```

   ⚠️ **이 모드는 우리 서버에 직접 물리면 안 된다.** 페이로드에 서명·타임스탬프를 넣을 수 없어 §3.4 인증이 성립하지 않는다. 반드시 아래 2번을 쓴다.

2. **WebSocket `/ws` + 클라이언트 (권장)** — `irispy-client`(Python) 또는 `node-iris`(TypeScript) 같은 클라이언트가 `/ws`로 실시간 수신하고, 답장은 `POST /reply` 로 보낸다 [14][22][23]:

   ```json
   { "type": "text", "room": "[CHAT_ROOM_ID]", "data": "[MESSAGE_TEXT]" }
   ```

   이 클라이언트가 곧 **런너측 글루(glue)** 다. 여기서 HMAC 서명을 붙여 우리 `/api/bot/command` 를 호출하고, 받은 `reply` 문자열을 `/reply` 로 흘려보낸다. 우리 서버는 이 글루의 존재만 알면 되고 Iris의 스키마는 몰라도 된다.

   기타 설정: DB 폴링 주기 `/config/dbrate`(ms), 전송 속도 `/config/sendrate`(ms), 봇 포트 `/config/botport` [14].

### 1.3 계열 비교 — 어느 쪽을 고를 것인가

| 항목 | A. 알림 리스너 (메신저봇R) | B. DB 관찰 (Iris) |
|---|---|---|
| 구축 난이도 | **낮음** — 앱 설치 + JS 스크립트 | 높음 — 루트/Redroid, 클라이언트 별도 구현 |
| 필요 하드웨어 | 안드로이드 폰 1대 상시 가동 | 폰 또는 **리눅스 서버 + Redroid 컨테이너** |
| 방 화면 진입 시 동작 | ❌ 멈춤 | ✅ 정상 |
| 알림 숨김/절전 영향 | ❌ 취약 | ✅ 무관 |
| 방 식별자 | 방 **이름 문자열** (이름 바뀌면 깨짐) | 카톡 내부 `chat_id` (안정) |
| 능동 전송(푸시) | `bot.send(room, msg)` — 세션 캐시 조건 있음(미확인) | `POST /reply` — 방 ID로 직접 |
| 카톡 업데이트 내성 | ❌ 낮음 | 중간 (DB 스키마 변경 시 영향) |

**권장:** 초기 검증은 **A(메신저봇R)** 로 빠르게, 실제 운영은 **B(Iris + Redroid)** 로 옮긴다. 우리 서버 인터페이스가 §3으로 고정되어 있으므로 이 전환에 **서버 코드 변경은 0줄**이다.

### 1.4 카카오톡 평문 출력 제약 — 응답 문자열 설계 규칙

봇의 답장은 **일반 카카오톡 채팅 메시지**다. 따라서:

| 제약 | 규칙 |
|---|---|
| **마크다운·HTML 전부 미지원** | `**굵게**`, `#제목`, `|표|`, `` `코드` `` 전부 리터럴로 그대로 보인다. **절대 쓰지 않는다.** |
| **가변폭 폰트** | 공백으로 열을 맞춘 표는 화면에서 어긋난다. **공백 패딩 정렬 금지.** `라벨: 값` 을 줄바꿈으로 나열한다. |
| 줄바꿈 | `\n` 만 사용. 연속 빈 줄은 1줄까지만(방이 지저분해진다). |
| **길이** | 카카오 공식 기준으로 **500자를 넘으면 "전체보기" 버튼으로 접힌다** (챗봇 텍스트형 말풍선 기준, 모바일톡·공백 제외 한글 글자수) [9]. 일반 채팅 말풍선의 정확한 접힘 기준은 **미확인**이나 같은 수준으로 보고 설계한다. → **우리 응답 예산: 350자 / 12줄 이내.** 초과분은 잘라내고 `자세히: https://…` 링크로 넘긴다. |
| 이모지 | 사용 가능. 상태 인코딩에 적극 활용(✅ ⏰ ❌ 🔴). 단 줄당 1~2개까지. |
| 구분선 | `───` 또는 `··············` 같은 문자 반복. 3~10자 이내로 짧게. |
| **동일 응답 연속 전송** | 런너의 도배 방지에 막힐 수 있다 [21] → §3.5 |
| 링크 | 카톡이 자동 링크화한다. 단축 URL 권장(말풍선이 길어지지 않게). |

## 2. 명령어 스펙 (초안) — 이번 산출물의 알맹이

접두어는 **`!`** 로 통일. **접두어 없는 메시지에는 절대 반응하지 않는다** (사람이 대화하는 방이다).
아래 "응답"은 **실제 카톡 화면에 보일 평문 그대로**다. 마크다운 없음, 공백 정렬 없음.

### 2.1 `!도움말`

```
입력:  !도움말
```
```
[M_Schedule] 명령어
───────────────
!일정        이번 주 파티 일정
!일정 오늘   오늘 일정만
!등록 <보스> <시간>   참여 등록
!취소 <보스>          참여 취소
!클리어 <보스>        클리어 체크
!결정석      이번 주 결정석 수익
!숙제        주간 숙제 현황
!환산 메검메   환산 스펙+스탯
!연결 <코드> 웹 계정 연결

웹: https://msch.app
```

### 2.2 `!일정`

```
입력:  !일정
```
```
📅 이번 주 파티 일정 (~8/20 목 00:00)
───────────────
⏰ 오늘 21:00 · 카오스 혼테일
   참가 5/6 · 미정 1
   우레푸, 라이언, 어피치, 프로도, 네오

  8/18(화) 22:00 · 하드 스우
   참가 3/6 · 모집중

  8/19(수) 20:30 · 하드 데미안
   참가 6/6 ✅ 확정

전체: https://msch.app/r/a7k2
```

- `⏰` = 24시간 이내, `✅` = 정원 충족, 무표시 = 그 외.
- **CLAUDE.md §4 도메인 규칙 적용**: 임박 경고는 red가 아니라 tertiary orange 계열 의미 — 평문에서는 `🔴` 대신 `⏰` 를 쓴다. red 계열 이모지는 실패/취소 전용.

#### ⛔ 스탯 스크래핑은 하지 않는다 — 만들었다가 하루 만에 걷어냈다 (2026-09-04)

2026-09-03 에 이 명령은 링크에 더해 **직업·레벨·환산·헥사환산·어센틱심볼**까지 이어지는 말풍선으로 붙였다(`features/bot/server/scouter.ts` + `scouter_stat_cache`). 동작은 했다. 그런데도 **전부 되돌렸다.** 아래는 왜 다시 시도하면 안 되는지의 기록이다.

**(a) 그 페이지는 껍데기만 서버 렌더라 HTML 로는 값이 없다 — 실측**

maplescouter `/ko/info` 를 `fetch` 로 받으면 **숫자가 한 개도 없다.** 스탯은 페이지가 브라우저에서 스스로 부르는 XHR(`/api/id?…`)로 오고, 그 응답이 화면에 그려진다. 즉 정적 HTML 파싱으로 얻을 수 있는 것은 `og:*` 태그뿐이고, **그건 카카오 카드가 이미 보여 주는 것**이다.

**(b) 그래서 헤드리스 브라우저가 유일한 길이었다**

값을 얻으려면 두 갈래뿐이다.
- 그쪽 내부 API(`api.maplescouter.com`)를 직접 호출 → **`viewer-key` 헤더를 요구한다.** 흉내내는 것은 접근제어 우회다.
- 페이지를 **헤드리스 브라우저로 열어** 그 브라우저가 받는 응답을 엿듣기 → 실제로 이렇게 구현했다(puppeteer-core + @sparticuz/chromium, 실측 0.9~2.0초/건).

두 번째가 "사람이 브라우저로 여는 것과 똑같다" 고 판단했는데, **그 판단이 틀렸다.**

**(c) 약관이 그 두 갈래를 모두 금지한다 — maplescouter 이용약관(2026-07-11 시행)**

발주자가 약관을 확인했고, 우리 구현이 **여섯 조항**에 걸렸다.

| 조항 | 내용 | 우리가 걸린 지점 |

**(d) 그래서 카드 링크만 남겼다 — 링크는 금지행위가 아니다**

> ⚠️ **다시 시도하지 말 것.** "HTML 만 파싱하면 되지 않나" 는 (a)가 막고, "브라우저로 열기만 하면 되지 않나" 는 (c)의 15조 1호가 이름을 대고 막는다. **스탯을 가져오는 경로가 전부 막혀 있다.** 되돌린 흔적: `handleScouter` 머리말 주석, 마이그레이션 `20260904120000_drop_scouter_cache.sql`.

**답장이 인코딩된 URL 한 줄인 이유** (발주자 실기 확인 2026-09-03)
- **퍼센트인코딩은 필수다** — 발주자 확인: *"퍼센트 인코딩 해줘야 카드로 뜸."* 한글이 섞인 URL 은 카카오의 스크랩 크롤러가 URL 로 집어내지 못해 **카드가 아예 만들어지지 않는다.**
  ⚠️ 초안은 반대로 갔다("브라우저가 알아서 인코딩하니 짧은 원문을 쓰자"). **그 판단은 링크를 누르는 경우만 봤다** — 카드를 그리는 주체는 브라우저가 아니라 카카오 크롤러다. 길이(한 글자당 9자)는 대가로 치른다.
- 카드 제목이 이미 닉네임을 보여 주므로 `🔍 <닉네임> 환산` 같은 앞줄은 **중복**이다. 카드는 URL 만 든 메시지에서 가장 확실히 뜬다 — 텍스트가 섞이면 생략되는 경우가 있다.
- maplescouter 는 닉네임별 `og:*` 를 **서버에서** 내려준다(실측). 이름 없는 URL 은 `" | 환산주스탯"` 이 되므로, **카드 제목의 이름 칸이 비어 보이면 이름이 URL 에 안 실렸다는 신호**다.
- ⚠️ 직전과 똑같은 `!환산` 을 연달아 치면 `differentiate()` 가 `· HH:mm` 을 붙여 URL 단독이 아니게 되고, 그때는 카드가 안 뜰 수 있다. 도배 방지를 우선해 그대로 둔다.

**인자 없음 / 형식이 틀린 경우** (침묵하지 않는다 — 명령은 정확히 쳤다)
```
입력:  !환산
```
```
!환산 메검메  처럼 닉네임을 붙여 주세요.
```
```
입력:  !환산 a!!
```
```
닉네임만 적어 주세요. (한글·영문·숫자 2~12자)
```

- **URL 실측 (2026-09-03)**
  - `GET /ko/info?name=<퍼센트인코딩된 닉네임>` → **HTTP 200**.
  - `GET /info?name=…` → **307** 로 `/ko/info` 로 리다이렉트. 그래서 `/ko` 를 붙인 형태를 쓴다 — 어차피 갈 곳이면 한 번 덜 튀는 편이 낫다.
  - 원문 UTF-8 바이트를 그대로 요청줄에 실으면 **400**. 링크를 *누르는* 경우는 브라우저가 알아서 인코딩해 주지만, **카드를 그리는 크롤러는 그 앞에서 멈춘다** — 그래서 우리가 인코딩해서 내보낸다(위 참조).
- **계정 연결을 요구하지 않는다.** 닉네임만 있으면 답이 나오는 **순수 문자열 변환**이라 `!연결` 안 한 사람도 쓸 수 있고, 핸들러가 **추가로 하는 조회는 0회**다 — `!웹` 과 같은 결이다. (스탯을 붙였던 하루 동안만 이것이 거짓이었다. 되돌아왔다.)
- **딸려 오던 라우트·번들 설정도 전부 원복했다**: `api/bot/command/route.ts` 의 `maxDuration = 60`, `next.config.ts` 의 `serverExternalPackages` + `outputFileTracingIncludes`, `.env.local.example` 의 `CHROME_PATH`, 의존성 `puppeteer-core` · `@sparticuz/chromium`. 남은 참조는 이 문서의 서술뿐이다.
- 페이지 주소 상수는 **`commands.ts` 의 `SCOUTER_BASE` 하나**가 소유한다. 주소가 바뀌면 고칠 곳도 한 곳이어야 한다.
- URL 안전성은 `encodeURIComponent` 가 맡는다. 그 앞의 **검증 정규식** `^[0-9A-Za-z가-힣]{2,12}$` 는 별개의 일을 한다 — **닉네임이 아닌 것을 링크로 만들어 주지 않는 것**. 공백은 검증 전에 전부 제거하므로 `!환산 메 검 메` 도 받아 준다.

### 2.9 `!연결 <코드>` — 본인 식별 (핵심)

**문제.** 카톡 방에서 얻을 수 있는 발신자 정보는 **닉네임 문자열뿐**이다 (계열 A는 `chat.author.name`, 계열 B는 `sender`) [14][17]. 오픈채팅 닉네임은 언제든 바뀌고 중복될 수 있으므로 **닉네임을 우리 DB의 키로 쓰면 안 된다.**

**흐름.**

```
1. 웹앱 로그인 → "카톡방 연결" → 6자리 코드 발급 (TTL 10분, 사용자당 동시 1개)
2. 방에서:  !연결 A7K2Q9
3. 런너가 POST /api/bot/command 로 전달 (sender.id 포함)
4. 서버가 코드 검증 → bot_channel_members 에
   (channel_id, sender_id) ↔ user_id 매핑 저장
5. 이후 sender.id 로 사용자 식별. 닉네임은 표시용으로만 사용.
```

`sender.id` 는 **런너가 제공하는 가장 안정적인 발신자 식별자를 런너가 골라 넣은 불투명 문자열**이다. 계열 B는 카톡 내부 `user_id`, 계열 A는 안정 ID가 없으므로 `sha256(방이름 + 닉네임)` 등 런너가 정한 값을 넣는다. **서버는 이 값의 의미를 해석하지 않는다.** 계열 A에서 닉네임이 바뀌면 재연결이 필요하다는 것이 이 방식의 알려진 한계다(→ §4 R4).

```
입력:  !연결 A7K2Q9
```
```
✅ 연결 완료
우레푸 (본캐: 우레푸 / 275)
이제 !등록 !클리어 를 쓸 수 있어요.
```

**실패**
```
❌ 코드가 맞지 않거나 만료됐어요.
https://msch.app/link 에서 새 코드를 받아주세요.
```
- 코드 5회 오입력 시 폐기, IP/방 단위 레이트리밋 적용 (§3.5).
- 연결 해제: `!연결해제` → 확인 1회 후 매핑 삭제.

### 2.10 파싱 규칙

**보스 별칭.** 별칭 → 보스ID 매핑은 **DB 테이블(`boss_aliases`)에 둔다. 코드에 하드코딩하지 않는다.** 신규 보스/신조어가 계속 생기므로 배포 없이 추가할 수 있어야 한다.

- 난이도 접두사를 분리해 인식: `이지/노말/카오스/하드/익스트림` 및 축약 `이/노/카/하/익`
  - 예: `하드스우`, `하스우`, `하드 스우` → (하드, 스우)
- 난이도 생략 시: 해당 방에서 그 보스로 **가장 최근 등록된 난이도**를 기본값으로 쓰고, 없으면 §2.4 되묻기.
- 공백 유무 무시, 대소문자 무시, 조사(`을/를/은/는`) 제거.
- **정확한 별칭 목록은 도메인 확정이 필요한 별도 작업이다.** 잘못된 별칭을 코드에 박으면 조용히 엉뚱한 보스에 등록된다.

**시간 표기 흔들림 허용.** 모두 **Asia/Seoul 고정 해석** 후 UTC(timestamptz)로 저장 (CLAUDE.md §2).

| 입력 | 해석 |
|---|---|
| `21시`, `21:00`, `2100`, `21` | 21:00 |
| `9시`, `9:00` | **09:00** (24시간제 그대로) |
| `오후9시`, `저녁9시`, `밤9시`, `9시(오후)` | 21:00 |
| `9시반`, `21시30분`, `21:30` | 21:30 |
| `목`, `목요일`, `목 21시`, `8/20 21시`, `20일 21시` | 해당 날짜 21:00 |
| 요일·날짜 생략 | **현재 주차(KST 목 00:00 경계) 내 다음 해당 시각**. 이미 지났으면 다음 주차로 넘기지 않고 되묻는다 |

- ⚠️ `9시`를 09:00으로 볼지 21:00으로 볼지는 실사용 혼선의 최대 원인이다. **위 표대로 24시간제로 고정하되, §2.4처럼 해석 결과를 항상 되돌려 보여준다.**
- 주차 계산은 반드시 **KST 목요일 00:00 경계**. ISO 주차를 쓰면 수·목요일이 두 주에 걸쳐 어긋난다 (CLAUDE.md §1).

### 2.11 응답 공통 규칙

- **미인식 명령(`!` 로 시작하지만 목록에 없음)은 침묵**한다. `알 수 없는 명령입니다` 남발은 방에서 쫓겨나는 지름길이다. 단, 편집거리 1 이내 오타는 1회만 `!일정 을 말씀하신 건가요?` 로 제안.
- 접두어 없는 일반 대화는 서버로 **보내지도 않는다** (런너에서 필터 — §4 R5 프라이버시).
- 에러 시 사용자 메시지는 항상 다음 형태로, 내부 정보 노출 금지.
  ```
  ⚠️ 잠시 문제가 생겼어요. 곧 다시 시도해 주세요.
  ```

## 3. 우리 서버 인터페이스 (확정)

버전은 경로에 박는다: `/api/bot/…` (v1 암묵). 계약 변경 시 `/api/bot/v2/…` 를 열고 유예 기간 병행.

### 3.1 `POST /api/bot/command` — 핵심 엔드포인트

**이 하나가 요구사항의 90%다.** 런너는 방에서 `!` 로 시작하는 메시지를 받으면 이걸 호출하고, 돌려받은 `reply` 문자열을 그대로 방에 뿌리면 끝이다.

**요청**

```
POST /api/bot/command
Content-Type: application/json
```
```json
{
  "room": "ch_01J8XK7Q2M4RSTV",
  "sender": {
    "id": "sd_9f3a1c72b8e4",
    "name": "우레푸"
  },
  "message": "!등록 카룡 21시",
  "timestamp": 1755432191,
  "signature": "v1=3a7f9c1e5b2d84a06f...",
  "nonce": "0f2e8b4a-31c7-4d9e-9a55-6b8d0e2f1c73"
}
```

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `room` | String | ✅ | **우리가 발급한 불투명 채널 ID.** 카톡 방 이름도 `chat_id`도 아니다 (§3.4) |
| `sender.id` | String | ✅ | 런너가 정한 안정적 발신자 식별자(불투명). 서버는 해석하지 않음 |
| `sender.name` | String | ✅ | 표시용 닉네임. **식별에 쓰지 않음** |
| `message` | String | ✅ | 원문 메시지. `!` 로 시작하는 것만 보낸다 |
| `timestamp` | Number | ✅ | Unix epoch **초** |
| `signature` | String | ✅ | `v1=` + HMAC-SHA256 hex (§3.4) |
| `nonce` | String | ✅ | 요청마다 유일한 UUID. 리플레이 방지 |

**응답 (200)**

```json
{ "reply": "✅ 등록 완료\n카오스 혼테일 · 8/17(월) 21:00\n참가 6/6 — 정원이 찼어요!" }
```

**이게 전부다.** `reply` 는 **카카오톡 평문 문자열 하나**이고, 런너는 이걸 `chat.reply(reply)` 또는 `POST /reply {"data": reply}` 에 그대로 넣는다. 런너가 렌더링·포맷·분기 판단을 할 일이 없다.

**침묵해야 할 때 (200)**

```json
{ "reply": null }
```
`null` 또는 빈 문자열이면 런너는 아무것도 보내지 않는다. (미인식 명령, 레이트리밋 초과 등)

**여러 말풍선으로 나눠야 할 때 (선택)**

```json
{ "reply": "…", "extra": ["두 번째 말풍선", "세 번째"] }
```
`extra` 는 선택 필드다. 미지원 런너는 무시하면 되고, 그래도 `reply` 하나는 온전히 동작한다 — **하위호환이 깨지지 않는 확장 규칙.**

**에러 응답**

| 상태 | 의미 | 런너 동작 |
|---|---|---|
| `200` | 정상 (`reply` 가 `null` 일 수 있음) | `reply` 있으면 전송 |
| `401` | 서명 불일치 / 타임스탬프 초과 | 전송 안 함. 로컬 로그만 |
| `404` | 미등록 `room` | 전송 안 함. 페어링 필요 상태로 표시 |
| `409` | `nonce` 재사용 (리플레이) | 전송 안 함 |
| `429` | 레이트리밋 초과 | 전송 안 함 (경고 메시지도 스팸이 된다) |
| `5xx` | 서버 오류 | 1회만 재시도(2초 후). 실패 시 침묵 |

> ⚠️ **명령 응답은 재시도 큐에 넣지 않는다.** 사람이 명령을 친 맥락은 수십 초만 지나도 사라진다. 실패하면 그냥 포기하는 게 맞다.

**서버 처리 예산.** 런너는 사람이 기다리는 대화창 앞에 있다. **`/api/bot/command` 타임아웃 3초**, 서버는 2초 안에 응답하도록 설계한다. 그 안에 못 끝낼 작업(넥슨 API 프록시 등)은 `reply` 로 "조회 중" 을 즉시 돌려주고 결과는 아웃박스(§3.3)로 보낸다.

### 3.2 `POST /api/bot/pair` — 방 최초 연결

부트스트랩 구간이라 **여기만 무서명**이다. 그래서 방어를 따로 건다.

**요청**
```json
{
  "code": "A7K2Q9",
  "runner": "iris/0.4.2",
  "room_fingerprint": "5c1d…"
}
```
- `code`: 웹앱에서 방장이 발급받은 6자리 코드 (TTL 10분)
- `room_fingerprint`: 런너가 계산한 방 지문 해시(재페어링 시 동일 방 확인용). 원문 방 이름은 보내지 않는다

**응답 (201)**
```json
{
  "room": "ch_01J8XK7Q2M4RSTV",
  "secret": "whsec_9f2a…",
  "poll_interval_sec": 30
}
```
`secret` 원문은 **이때 딱 한 번만** 노출된다. 서버는 해시로만 보관한다 (CLAUDE.md §2.1의 API 키 원칙과 동일 기조).

방어: IP당 분당 5회, 코드 5회 오입력 시 폐기, 코드는 1회용.
회전: `POST /api/bot/rotate`(서명 필요) → 신규 시크릿 발급, 구 시크릿 24시간 병행 검증.

### 3.3 `GET /api/bot/outbox` / `POST /api/bot/outbox/ack` — 선제 알림 (부)

**왜 폴링인가.** 봇 런너는 가정용 안드로이드 폰이거나 NAT 뒤 컨테이너다. 공인 IP·인바운드 포트가 없으므로 **서버가 런너를 부를 수 없다.** 런너가 주기적으로 가져가는 방식이 유일하게 확실하다.

**요청**
```
GET /api/bot/outbox?room=ch_01J8XK7Q2M4RSTV&max=5&wait=25
X-MS-Timestamp: 1755432191
X-MS-Nonce: 0f2e8b4a-…
X-MS-Signature: v1=3a7f…
```
- `wait`: 롱폴링 대기 초(0이면 즉시 응답). 미지원 런너는 생략하고 30초 간격 단순 폴링해도 동작한다.

**응답**
```json
{
  "server_time": 1755432192,
  "messages": [
    {
      "id": "dl_01J8Y2K4P7Q",
      "reply": "⏰ 30분 전 알림\n카오스 혼테일 · 오늘 21:00\n참가 5/6 · 미확정 1명\n!일정 으로 확인",
      "expires_at": 1755434100
    }
  ]
}
```

`reply` 필드명을 §3.1과 **일부러 동일하게** 맞췄다. 런너 입장에서는 "어디서 왔든 `reply` 문자열을 방에 뿌린다"는 규칙 하나만 구현하면 된다.

**전송 확인 (ack)**
```
POST /api/bot/outbox/ack
```
```json
{
  "room": "ch_01J8XK7Q2M4RSTV",
  "results": [
    { "id": "dl_01J8Y2K4P7Q", "status": "sent" },
    { "id": "dl_01J8Y2K4P7R", "status": "failed", "error": "room_not_found" }
  ]
}
```

**중복 발송 방지 — 3중 방어**

1. **`dedupe_key` (적재 시점).** `bot_outbox(room, dedupe_key)` 유니크 인덱스. 규약: `{목적}:{엔티티ID}:{시점}`
   - 예: `boss_remind:sch_9931:T-30`, `crystal_weekly:ch_01J8X:2026-W34-KST`
   - 스케줄러가 중복 실행되거나 크래시 후 재실행돼도 같은 행에 부딪혀 삽입이 거부된다.
   - ⚠️ 주차 표기는 **KST 목요일 00:00 경계 기준**. ISO 주차를 쓰면 수·목 알림이 두 주에 걸쳐 중복 생성된다.
2. **`id` 멱등 (전송 시점).** 런너는 이미 `sent` 로 ack한 `id` 를 다시 받으면 재전송하지 않고 ack만 되풀이한다.
3. **리스(lease).** 응답 시 각 메시지에 `visible_after = now + 60s` 를 건다. 폰 교체 중 런너 두 개가 동시에 붙어도 같은 건을 중복으로 집어가지 않는다.

**재시도와 만료**

- ack 없는 건은 지수 백오프로 재노출: 30s → 2m → 5m → 15m → 30m (최대 5회).
- `status: "failed"` + 비재시도 오류(`room_not_found`, `permission_denied`)면 즉시 중단, 채널을 `degraded` 로 표시하고 웹앱에 배너.
- **`expires_at` 경과 시 폐기.** 이 도메인에서 특히 중요하다 — "30분 전 알림"이 보스 시간이 지나 도착하면 가치가 음수다. 기본 TTL: 리마인더 15분, 주간 요약 6시간.
- 채널이 24시간 이상 폴링 없음 → 적재 중단. 죽은 런너 뒤에 알림이 쌓였다가 복구 순간 수십 건이 한꺼번에 터지는 사고를 막는다.

### 3.4 인증 — 방별 토큰 + HMAC 서명

**서명 계산**

```
base   = "{timestamp}.{nonce}.{METHOD}.{path}.{sha256_hex(raw_body)}"
sig    = "v1=" + hex(HMAC_SHA256(channel_secret, base))
```

- GET 요청은 `raw_body` 를 빈 문자열로 두고 쿼리스트링 포함 `path` 를 쓴다.
- `POST /api/bot/command` 는 `signature`/`nonce`/`timestamp` 를 **본문 필드로** 받는다(런너 스크립트가 커스텀 헤더를 못 붙이는 경우가 있어서다). 서명 계산 시 `raw_body` 는 **`signature` 필드를 제외한 나머지를 키 정렬해 직렬화한 JSON**으로 정의한다. 다른 엔드포인트는 `X-MS-Timestamp` / `X-MS-Nonce` / `X-MS-Signature` 헤더를 쓴다.

**검증 규칙**

| 항목 | 규칙 |
|---|---|
| 타임스탬프 | 서버 시각 대비 **±300초** 이내. 초과 시 `401` |
| nonce | 방별 10분 캐시. 재사용 시 `409` |
| 비교 | **상수 시간 비교** (타이밍 공격 방지) |
| 시크릿 | 서버는 **해시로만** 보관. 원문은 페어링 응답 1회만 노출 |
| 실패 로깅 | 서명 실패는 방 단위로 카운트, 10분 내 20회 초과 시 채널 일시 정지 |

**⚠️ 계열 A(메신저봇R)의 HMAC 계산 가능 여부는 미확인.** Rhino가 `org.jsoup` 등 Java 클래스를 직접 호출하는 것이 확인되었으므로 [13][20] 같은 경로로 `javax.crypto.Mac` 을 쓸 수 있을 것으로 보이나 **실측되지 않았다.** 불가로 판명되면 계열 A에 한해 대체안이 필요하다: (a) 폰에서 로컬 프록시(Termux 등)를 거쳐 서명, (b) 계열 A는 `Authorization: Bearer <secret>` + TLS + 타임스탬프만으로 낮춰 운영하고 계열 B에서만 서명 강제. **어느 쪽이든 서버는 두 방식을 모두 받도록 설계하되, 서명 미사용 채널은 별도 플래그로 표시하고 아웃박스 발송 권한을 제한한다.**

**RLS.** `bot_channels` / `bot_channel_members` / `bot_outbox` / `bot_command_log` 전부 RLS 필수. 봇 트래픽은 사용자 세션이 아니라 채널 시크릿으로 인증되므로 RLS로는 보호되지 않는다 → **anon/authenticated 역할 전면 차단**, Route Handler에서 서명 검증을 통과한 뒤에만 service role 클라이언트를 쓴다.

### 3.5 레이트리밋 · 도배 방지

| 대상 | 한도 | 초과 시 |
|---|---|---|
| 방(`room`)당 `/api/bot/command` | 분당 20회 | `429` + `reply: null` (침묵 드롭) |
| 발신자(`sender.id`)당 | 분당 6회 | 동일 |
| `/api/bot/pair` (IP당) | 분당 5회 | `429` |
| 아웃박스 발송 (방당) | 시간당 10건 | 초과분 적재 거부 + 서버 경고 로그 |

**동일 응답 연속 전송 문제.** 런너의 도배 방지에 막힐 수 있으므로 [21], 서버는 **직전 응답과 완전히 동일한 문자열을 연속으로 내보내지 않는다.** 동일해질 경우 말미에 시각(`· 21:04` 등) 한 조각을 덧붙여 차이를 만든다. 런너 설정에서 도배 방지를 끄는 것도 가능하지만 [21], **서버 쪽 방어를 기본으로 둬야 런너가 바뀌어도 안전하다.**

### 3.6 런너 비종속 — 금지 목록

우리 서버 코드/스키마에 아래가 등장하면 그 순간 설계가 깨진 것이다.

- ❌ `kakao_chat_id`, `openlink_id`, **카톡 방 이름 문자열**을 컬럼으로 저장
- ❌ Iris의 `/reply`, 메신저봇R의 `chat.reply` 등 **특정 런너 API를 서버가 직접 호출**
- ❌ 런너 종류에 따른 **분기 로직** (런너 문자열은 로그·통계 전용)
- ❌ 응답에 카카오 전용 UI 구조(버튼/캐러셀) 넣기
- ✅ `room` 은 **우리가 발급한 불투명 ID.** `room ↔ 실제 방`의 매핑은 **런너가 자기 로컬에 보관**한다. 계열 A는 방 이름, 계열 B는 `chat_id` 로 서로 호환되지 않는 값을 쓰는데, 이 한 줄이 그 차이를 서버 밖으로 밀어낸다.
- ✅ 출력은 **평문 문자열 하나(`reply`)** 가 1급 시민. 확장은 `extra` 처럼 **무시해도 동작하는** 선택 필드로만.

이 규약을 지키면 카카오 경로가 막히거나 리스크가 감당 불가로 판단될 때, **텔레그램/디스코드 런너를 새로 붙이는 작업이 서버 변경 0줄**로 끝난다. 두 플랫폼 모두 무료 공식 Bot API가 있고, 위 계약을 만족시키는 글루는 수십 줄이면 된다.

### 3.7 최소 DB 스키마 (설계만 — 마이그레이션은 별도 작업)

| 테이블 | 주요 컬럼 |
|---|---|
| `bot_channels` | `room`(PK, 불투명 ID), `platform`, `secret_hash`, `owner_user_id`, `status`(active/degraded/paused), `signed`(bool), `last_seen_at` |
| `bot_channel_members` | `room`, `sender_id`(런너 제공 불투명값), `user_id`, `display_name`(표시용), `linked_at` |
| `bot_outbox` | `id`, `room`, `dedupe_key`(UNIQUE with room), `reply`, `expires_at`, `visible_after`, `attempts`, `state` |
| `bot_command_log` | `nonce`(UNIQUE with room), `room`, `sender_id`, `command`, `result`, `created_at` — 리플레이 방지 + 감사. **명령 원문만 저장, 일반 대화는 저장하지 않음** |
| `boss_aliases` | `alias`, `boss_id`, `difficulty` — §2.10. 코드 하드코딩 금지 |

## 4. 리스크 및 발주자에게 알려야 할 사항

### R1. 공식 지원이 없다 🔴

오픈채팅방 봇은 카카오가 **의도적으로 막아둔** 영역이다. "아직 안 나왔다"가 아니라 "안 만든다"에 가까운 공식 답변이 두 건 있다 [1][2]. 향후 개방 가능성은 **미확인**이며, 카카오는 개선 요청 창구로 고객센터/제휴 제안만 안내한다. 제휴를 통해 오픈채팅 API가 실제 제공된 사례가 있는지도 **미확인**.

### R2. 계정 제재 가능성 🔴 — 가장 중요

카카오톡 운영정책이 명시적으로 금지하는 항목 [10]:

- "카카오가 허용하지 않은 비정상적인 프로그램 등을 이용하여 카카오톡의 프로토콜·API 등을 부정하게 호출하는 행위"
- "카카오톡의 프로토콜·API 등을 악용한 프로그램(봇, 매크로, 웹사이트 등)을 개발·제작하여 이를 유상 또는 무상으로 타인에게 유포·제공하는 행위"

위반 시 "카카오톡 **전체 서비스**에 대한 이용을 한시적 또는 영구적으로 제한"할 수 있다 [10]. 오픈채팅 제재 수위는 최소 1일 ~ 최대 60일이며 중대 위반 시 영구 제한, **참여자 개인의 위반으로 오픈채팅방 자체에 규제 조치**가 내려질 수 있다 [11].

**전례:** 2021년 3월 3일 카카오톡 봇 계정과 **계정 소유자의 본계정까지 대규모로 정지**된 사건이 있었다 [12].

발주자가 반드시 이해해야 할 것:
- 제재 대상이 봇 계정에 그치지 않을 수 있다. **본계정 연쇄 정지 전례가 있다.** → **반드시 부계정 + 전용 단말**로 운영.
- 방이 통째로 제재받을 수 있어 **다른 참여자에게도 영향**이 간다.
- 우리가 만드는 것은 서버이지 런너가 아니다. 다만 **런너를 우리가 배포·재판매하면** 위 "유포·제공" 조항에 정면으로 걸린다. 이 선은 넘지 않는다.
- **이 리스크는 설계로 제거할 수 없다.** 감수 여부는 발주자 결정 사항이다.

### R3. 운영 안정성 🟠

- **카카오톡 앱이 업데이트되면 봇이 죽을 수 있다** [12][13]. 계열 A는 알림 구조 변경에, 계열 B는 DB 스키마 변경에 각각 취약하다. 복구는 우리가 아니라 오픈소스 런너 유지보수자의 속도에 달려 있다.
- 계열 A는 **봇 폰의 화면이 켜져 그 방에 들어가 있으면 아예 반응하지 않는다** [21]. 사람이 쓰던 폰에서 돌리면 안 된다.
- 전용 단말 24시간 가동(전력, 배터리 스웰링, 통신비) 또는 리눅스 서버 + Redroid 컨테이너 [15]. **알림 하나 보내자고 단말 한 대를 상시 돌려야 한다.**
- 봇 계정 생성용 전화번호가 별도로 필요하다.

### R4. 닉네임 기반 식별의 한계 🟠

계열 A는 발신자를 **닉네임 문자열로만** 알 수 있다 [17]. 그래서 §2.9의 `!연결` 페어링이 필수이고, **오픈채팅 닉네임을 바꾸면 재연결이 필요**할 수 있다. 발주자 관점에서는 "봇을 초대하면 자동으로 다 되는" 게 아니라 **방 최초 1회 + 사용자마다 1회 연결 절차**가 있다는 뜻이다. 계열 B는 카톡 내부 `user_id` 를 쓸 수 있어 이 문제가 없다 [14].

### R5. 프라이버시 🟠

봇 런너는 원리상 그 방의 **모든 메시지**를 읽는다(알림이든 DB든). 따라서:

- **런너에서 `!` 로 시작하는 메시지만 필터링해 서버로 보낸다.** 일반 대화는 우리 서버에 도달하지 않는다.
- 서버 `bot_command_log` 에도 **명령 원문만** 저장한다.
- 방 참여자에게 봇의 존재와 동작 범위를 고지해야 한다(공지 또는 봇의 입장 메시지).

### R6. 권장 진행 순서

| 단계 | 내용 | 리스크 |
|---|---|---|
| 1 | 서버에 §3 인터페이스 구현 (`/api/bot/command` 우선, 아웃박스는 후순위) | **0** — 카카오톡을 전혀 건드리지 않음 |
| 2 | 텔레그램 또는 디스코드 봇으로 글루를 붙여 §2 명령어 전체를 실제로 검증 | **0** — 공식 무료 Bot API |
| 3 | 메신저봇R + 부계정 + 전용 폰으로 카카오 경로 시범 운영 | **높음 — 발주자 승인 필수** |
| 4 | 안정화 시 Iris + Redroid 로 이관 (서버 변경 0줄) | 높음 |
| 보조 | 개인 단위 리마인더는 공식 "나에게 보내기" 제공. 발송 제한·검수 없음 [4]. 단 **방 공유 불가** | **0** |
| 보조 | "주간 초기화됐습니다" 같은 **고정 문구 정기 알림**은 카카오 공식 방장봇 정시 알림으로 분리 [7][8] | **0** |

**1·2단계는 지금 바로 착수 가능하며, 3단계 승인이 나지 않아도 버려지는 작업이 없다.**

### 미확인 항목

- **메신저봇R(Rhino)에서 `javax.crypto.Mac` 으로 HMAC-SHA256을 계산할 수 있는지** — `org.jsoup` 등 Java 클래스 직접 호출은 확인되었으나 [13][20] `javax.crypto` 사용은 실측 미확인. §3.4의 인증 방식 확정에 직결되므로 **구현 착수 전 실기기 검증 필요.**
- **`bot.send(room, msg)` 로 알림을 한 번도 받지 않은 방에 최초 메시지를 보낼 수 있는지**, 재부팅 후 세션 캐시 소실 여부 — 공식 문서에 `canReply(room)` 로 사전 확인하라고만 되어 있고 조건은 명시 없음 [16]. **아웃박스(선제 알림)의 실현 가능성에 직결.** Iris는 방 ID로 직접 전송하므로 이 제약이 없어 보이나 이 역시 실측 미확인.
- **일반 카카오톡 채팅 말풍선의 "전체보기" 접힘 정확한 기준** — 500자 기준은 챗봇 텍스트형 말풍선 공식 문서 기준이며 [9], 일반 채팅 말풍선에 동일 적용되는지는 미확인. 본 문서는 보수적으로 350자 예산을 잡았다.
- **카카오톡 일반 채팅의 최대 글자수 하드 리밋** — 공식 문서에 명시 없음.
- **봇 런너들의 현재(2026년 8월) 실동작 여부** — 카카오톡 앱 업데이트에 따라 수시 변동. 본 문서는 각 프로젝트 문서 기준이며 실동작은 미확인.
- **카카오 제휴(파트너) 계약을 통한 오픈채팅 API 제공 사례 존재 여부** — 데브톡 답변은 제휴 창구만 안내할 뿐 사례를 밝히지 않음 [1].
- **메이플스토리 보스 별칭 정확한 매핑표** — §2.10의 예시(`카룡` 등)는 형식 설명용이다. 실제 별칭·난이도 매핑은 도메인 확정이 필요한 별도 작업이며, 잘못 박으면 조용히 엉뚱한 보스에 등록된다. `boss_aliases` 테이블로 관리한다.
