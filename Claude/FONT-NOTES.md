# FONT-NOTES — 기본 UI 서체를 메이플스토리체로 교체

작성일 2026-08-18 · 대상 커밋 기준 파일: `src/app/layout.tsx`, `src/app/globals.css`,
`src/app/fonts/**`

이 문서는 `Claude/pipelinepro-DESIGN.md` 를 **대체하지 않는다.** 디자인 원문은 수정 금지이고
(CLAUDE.md §4), 서체 대체 사실과 그 근거는 이 사이드 노트에 남긴다.
`Claude/DARK-PALETTE.md` §6-1(타이포그래피 절)은 IBM Plex Sans KR 을 전제로 쓰여 있어
**이 문서 이후로는 옛 기록**이다. 행간 조정(6-1 "행간 — 헤딩만 조정")과 유동 타입 스케일
(6-2)은 서체와 무관하게 그대로 유효하다.

## 1. 왜 바꿨나

발주 원문: *"글씨체 뭔지 모르겠는데 너무 보기 불편함. 메이플스토리체 적용해줘."*

서체 이력은 이렇게 흘렀다.

| 시점 | 서체 | 끝난 이유 |
|---|---|---|
| 초기 | Outfit(제목) + Inter(본문) | **둘 다 한글 글리프가 없다.** 모든 한글이 OS 기본 폰트로 떨어져 머신마다 다르게 보였다 |
| 직전 | IBM Plex Sans KR | 위 문제는 해결했으나 발주자가 "무슨 글씨인지 모르겠고 불편하다"고 판단 |
| **현재** | **메이플스토리체 (Maplestory OTF Light / Bold)** | — |

CLAUDE.md §4 는 이미 이 교체를 허용한다. 디자인 원문이 지정한 Outfit/Inter 는 한글이 없어
**"한글 지원 서체를 기본 UI 폰트로 삼는다"** 가 이 저장소의 규정이고, 메이플스토리체는 그
규정에 부합한다. 덤으로 제품 주제(메이플스토리 보스 스케줄러)와 일치한다.

바뀌지 않은 것:

- **헤드라인과 본문은 여전히 한 패밀리다.** `--font-headline` 과 `--font-sans` 가 같은 값을
  가리킨다. 제목만 다른 서체를 쓰면 한국어 제목에서 폰트가 갈린다.
- **Mono 는 Source Code Pro 그대로다**(§4 규정). API 키·ocid·코드 표시 전용이고 한글이
  들어가지 않는다. 아래 §6 의 등폭 숫자 문제 때문에 오히려 더 중요해졌다.
- **런타임 외부 폰트 CDN 요청 0건.** 예전에는 `next/font/google` 이 빌드 시점에 받아
  self-host 했고, 지금은 저장소에 벤더링한 woff2 를 `next/font/local` 이 서빙한다.
  결과는 같다 — 브라우저는 우리 오리진 밖으로 폰트를 받으러 가지 않는다.

## 3. 포맷 변환을 어떻게 처리했나 (판단이 필요했던 지점)

메이플스토리체는 **Google Fonts 에 없다.** `next/font/google` 로는 불가능하고, 넥슨은
OTF/TTF 만 배포한다. 웹에서 쓰려면 woff2 가 필요하다.

한 것:

- 넥슨 공식 `MaplestoryFont_OTF.zip` 을 직접 내려받아
- `fontTools 4.63.0` 으로 **컨테이너만 woff2 로 재압축**했다
  (`TTFont(otf).flavor = "woff2"; save()`)

하지 **않은** 것:

- 글리프(CFF 아웃라인) 수정 — 없음
- **서브셋 — 하지 않았다.** 원본 12,259 글리프 / 12,255 코드포인트가 변환 후에도 그대로
  남아 있음을 확인했다(한글 완성형 11,172자 전부 포함)
- name 테이블·OS/2 가중치(300/700)·메트릭 — 전부 원본 그대로
- 규격상 유효할 수 없는 DSIG(디지털 서명)만 변환기가 제거했다. 브라우저는 DSIG 를 읽지 않는다

**"임의로 수정·편집 불가, 배포되는 형태 그대로" 조항을 어떻게 읽었는가.** 이 조항은
글자꼴 자체의 변형(리디자인·서브셋·개명)을 막는 것으로 해석했다. 같은 라이선스가 바로
다음 문장에서 "임베디드 폰트로 사용"을 허용하는데, 웹에서 임베디드 폰트란 곧 woff/woff2 다.
서브셋을 일부러 하지 않은 것도 이 해석에 맞추기 위해서다(용량은 커지지만 원형은 남는다).
그럼에도 이건 우리 쪽 해석이므로, 원본 zip 안 OTF 의 sha256 을
`src/app/fonts/LICENSE-Maplestory.txt` 에 남겨 "우리가 배포하는 것이 넥슨 원본과 같은
글자꼴"임을 언제든 검증할 수 있게 했다.

> 대안으로 이미 woff2 로 배포 중인 공개 사본(`github.com/fonts-archive/Maplestory`)도
> 검토했다. 그 저장소의 OTF 파일 크기가 넥슨 원본과 정확히 일치해 신뢰할 만하지만,
> **공식 배포처에서 직접 받는 쪽이 출처가 더 짧아** 그쪽을 택했다.

## 4. 굵기 매핑 — 실제 2단을 타입 스케일 4단에 붙이기

메이플스토리체는 **Light(OS/2 300) 과 Bold(OS/2 700) 두 벌뿐이다.** 그런데
`src/app/globals.css` 의 타입 스케일은 네 단계를 쓴다.

| 토큰 | font-weight | 성격 |
|---|---|---|
| `--text-display` 52px | 700 | 제목 |
| `--text-headline` 38px | 700 | 제목 |
| `--text-subhead` 26px | 600 | 제목 |
| `--text-body-lg` / `body` / `body-sm` / `code` | 400 | 본문 |
| `--text-label` 13px / `--text-caption` 12px | 500 | 라벨 |
| `--text-overline` 11px | 700 | 눈썹 라벨 |

코드베이스의 Tailwind 굵기 클래스 사용 빈도도 같이 봤다:
`font-semibold`(600) 68회 · `font-medium`(500) 9회 · `font-bold`(700) 5회 · `font-normal`(400) 2회.

### 결정

`@font-face` 를 굵기 **구간**으로 선언한다.

```
Maplestory-Light.woff2  →  font-weight: 300 500
Maplestory-Bold.woff2   →  font-weight: 600 900
```

결과 매핑:

| 요청 굵기 | 실제 렌더 | 합성 볼드 |
|---|---|---|
| 300 / 400 / 500 | Maplestory **Light** | 없음 |
| 600 / 700 / 800 / 900 | Maplestory **Bold** | 없음 |

### 왜 이렇게 했나

1. **합성 볼드를 원천 차단한다.** 각 face 를 `300` / `700` 단일 값으로 선언하면 500·600 은
   브라우저 매칭 알고리즘에 맡겨진다. 지금의 크롬/사파리 규칙에서는 우연히 같은 결과가
   나오지만, 규칙에서 조금만 벗어나거나 누군가 `font-black`(900) 을 쓰는 순간 **가짜 굵게**가
   끼어들어 작은 한글이 뭉갠다. 구간으로 선언하면 300~900 어떤 값이 와도 실제 face 가
   하나 잡히므로 합성이 발생할 여지가 없다.
   (정적 폰트에 굵기 구간을 선언하는 것은 CSS `@font-face` 스펙상 유효하다. `next/font/local`
   은 `weight` 문자열을 `@font-face { font-weight: ... }` 에 그대로 써 준다 —
   `node_modules/next/dist/compiled/@next/font/dist/local/loader.js` 확인.)
2. **경계를 500|600 에 둔 이유.** 타입 스케일에서 500 은 `label`·`caption`, 즉 *본문처럼
   읽혀야 하는* 것이고, 600 은 `subhead` 와 전역 `font-semibold`(68회), 즉 *강조로 읽혀야
   하는* 것이다. 실제 의미의 경계가 정확히 거기다. 600 을 Light 쪽에 붙이면 화면 전역의
   강조가 사라지고, 500 을 Bold 쪽에 붙이면 12–13px 라벨이 전부 굵어져 무거워진다.
3. **`--text-overline`(11px / 700) 은 Bold 로 간다.** 이게 이 매핑에서 가장 빡빡한 자리다 —
   §5 참고.

### 폰트 로딩 전략

`display: "swap"` 유지(변경 없음). `preload: false` 유지 — 다만 **이유가 바뀌었다.**

- 예전 이유: 구글 한글 폰트는 unicode-range 로 수백 조각이라 preload 링크가 쏟아진다
- 지금 이유: 조각은 2개뿐이지만 **합계 약 468KB** 라, 모든 페이지 `<head>` 에서 최우선순위로
  받게 하면 JS/CSS 와 대역을 다툰다

`next/font` 의 자동 폴백 메트릭 보정은 그대로 켜 둔다(`adjustFontFallback` 기본값 = Arial).
Light face 기준으로 계산되는 값은 `size-adjust ≈ 112.51%`, `ascent-override ≈ 75.55%`,
`descent-override ≈ 23.55%` 다 — 메이플스토리체 라틴 소문자가 Arial 보다 넓어서 폴백을
키우는 방향이다. 한글에는 이 보정이 닿지 않는다(Arial 에 한글이 없어 체인 다음으로 넘어간다).

폴백 체인은 두 군데에 모두 적는다: `next/font/local` 의 `fallback` 옵션과
`globals.css` 의 `--font-sans` / `--font-headline` 값 (`ui-sans-serif, system-ui, sans-serif`).
중복이지만 폰트 로드 실패가 빈 화면이 되면 안 된다.

## 5. 작은 크기(11px / 12px) 가독성 실측

§4 가독성 규칙: 문장은 14px 미만 금지, 11px(`overline`)·12px(`caption`)은 배지·라벨·수치
주석 전용. 메이플스토리체는 장식성이 있어 작은 크기가 위험할 수 있다고 보고 실제로 재 봤다.

### 방법

FreeType 으로 실제 UI 문자열을 1x(96dpi 상당)와 2x(레티나 상당)로 래스터화해 눈으로 확인하고,
같은 문자열을 **직전 서체 IBM Plex Sans KR 400** 으로 나란히 렌더해 비교했다.
브라우저 힌팅과 완전히 같지는 않지만 판단에는 충분하다.

### 계측값

| 항목 | Maplestory Light | IBM Plex Sans KR 400 |
|---|---|---|
| unitsPerEm | 1000 | 1000 |
| x-height | **479** (0.479em) | 516 (0.516em) |
| cap height | 678 | 698 |
| hhea ascent / descent | 850 / −265 | — |

라틴 소문자 기준으로 **x-height 가 7.2% 작다.** 같은 `font-size` 에서 라틴이 조금 작아
보인다는 뜻이다.

### 눈으로 본 결과

- **한글은 오히려 직전보다 굵고 크다.** x-height 가 작은 것은 라틴 이야기고, 한글은 글자틀
  자체가 크고(전각 860~900/1000) 획이 두껍다. "Light" 라는 이름과 달리 한글 본문은 Plex
  Regular 보다 **진하게** 보인다. 걱정했던 "얇아서 안 보임"은 일어나지 않았다.
- **14px(`body-sm`) / 13px(`label`) / 12px(`caption`) 은 문제 없다.** 1x 에서도 속공간이
  살아 있고 Plex 대비 오히려 또렷하다.
- **11px `text-overline` 이 유일하게 빡빡하다.** 이 토큰만 `font-weight: 700` 이라
  **Bold face** 로 떨어지는데, 11px 한글 + Bold 는 1x 화면에서 획이 서로 붙기 시작한다
  (`결정석` 의 속공간이 거의 메워진다). 다만 이 토큰에는 `letter-spacing: 0.09em` 이 이미
  걸려 있어 그 덕에 **읽히기는 한다**. 사용처도 14곳뿐이고 전부 `M_Schedule`, `내 스케줄`,
  카드 눈썹 라벨 같은 짧은 문구다.

### 판단은 발주자 몫 — 크기를 임의로 바꾸지 않았다

`--text-overline` 을 건드리지 않았다. 필요하다면 아래 중 하나가 답인데, 셋 다 디자인 결정이라
여기서 고르지 않았다.

| 안 | 내용 | 대가 |
|---|---|---|
| A | 그대로 둔다 | 11px 눈썹 라벨이 직전보다 조금 답답하다 |
| B | `--text-overline--font-weight` 를 700 → 500 으로 (11px 유지) | Light face 로 떨어져 숨통이 트인다. 눈썹 라벨의 강조가 약해진다 |
| C | `@font-face` 에 `size-adjust` 를 얹어 글자를 통째로 ~7% 키운다 | 모든 px 토큰을 그대로 두고 체감 크기만 회복한다. 대신 줄바꿈 위치가 전부 바뀐다 |

## 6. 알려진 손실 — 이 서체로 바꾸면서 생긴 것

### 6-1. `tabular-nums` 가 무효가 된다 ⚠️

메이플스토리체는 **GSUB 테이블이 비어 있다**(피처 0개). `tnum`(등폭 숫자) 피처가 없고,
기본 숫자 자체도 등폭이 아니다.

```
숫자 advance width (upem 1000)
0:675  1:432  2:607  3:601  4:664  5:567  6:600  7:537  8:638  9:605
```

`1` 이 `0` 의 64% 폭이다. 코드 전역에서 `tabular-nums` 를 **24개 파일 46곳**에 쓰고 있는데
(메소 금액, `10/12` 카운터, `21:00` 시각, 주차 키, 좌석 번호 …) 이 서체에서는 전부
**아무 효과가 없다.** 세로로 쌓인 금액의 자릿수가 어긋나 보일 수 있다.

직전 IBM Plex Sans KR 은 숫자가 등폭이었으므로 이건 **명백한 회귀**다. 선택지:

- 그대로 둔다 (대부분의 화면은 금액이 세로로 여러 줄 쌓이지 않는다)
- 자릿수 정렬이 정말 필요한 자리(수익 표)만 `font-mono` 로 바꾼다 — Source Code Pro 는
  등폭이므로 즉시 해결된다. 다만 그 자리만 서체가 갈린다
- 숫자에만 `unicode-range` 로 다른 서체를 물린다 — 한 줄 안에서 서체가 갈리므로 권하지 않는다

**→ 결정됨 (2026-08-18). §9 참고 — 두 번째 선택지("정말 필요한 자리만 mono")를 골랐다.**

### 6-2. 없는 글리프 — `—` `–` `•`

앱 소스 전체(`src/**/*.{ts,tsx,css}`)의 문자를 폰트 cmap 과 대조한 결과, 화면에 실제로
나오는 문자 중 이 서체에 **없는** 것:

| 문자 | 이름 | 실제 사용처 | 영향 |
|---|---|---|---|
| `—` U+2014 | em dash | `src/app/income/page.tsx:108` 본문, `<title>` 문자열 | 그 글자만 폴백 폰트로 떨어진다 |
| `–` U+2013 | en dash | `src/app/showcase/page.tsx:359-360` (개발용 경로) | 위와 같음 |
| `•` U+2022 | bullet | `src/features/auth/lib/api-key.ts` 키 마스킹 | **영향 없음** — 마스킹된 키는 `font-mono` 로 렌더되고 Source Code Pro 에는 있다 |
| `⚠ ✅ ❌ 🖼` | 이모지 | 여러 곳 | 정상. 이모지는 원래 OS 이모지 폰트가 그린다 |

문제는 `—` 다. 한 문장 안에서 그 글자만 다른 서체로 떨어지는데, 이건 예전에 Outfit/Inter 를
버린 바로 그 증상("한 줄에 두 폰트가 이어 붙음")의 축소판이다. 본문 문장에서는 `—` 를
`·` 이나 `-` 로 바꾸는 편이 낫다 — 다만 그건 문안 수정이라 이번 작업 범위 밖이다.

반대로 **`·`(U+00B7) 와 `…`(U+2026) 는 있다.** 이 앱이 가장 많이 쓰는 구분자
(`카오스 칼로스 · Lv.295 · 21:00`)는 안전하다.

### 6-3. 라틴 대문자의 장식성

`I` 같은 대문자에 위아래 가로획이 있어(폭 395/1000) 라틴 전용 줄은 디스플레이 서체처럼
읽힌다. `WEEKLY BOSS` 같은 `uppercase` 눈썹 라벨에서는 오히려 또렷하고 보기 좋았다.
긴 영문 문장에는 적합하지 않지만 이 앱에 그런 화면은 없다.

## 9. 등폭 숫자 — 무엇을 mono 로 바꿨고 무엇을 안 바꿨나 (2026-08-18 결정)

§6-1 이 남겨 둔 선택지 중 **두 번째**를 골랐다.

> 발주 원문: *"핵심 숫자만."*

전부 바꾸지 않았다. §6-1 의 세 선택지 중 "그대로 둔다"는 세로로 쌓이는 금액이 실제로
어긋나므로 기각했고, "숫자에만 `unicode-range` 로 다른 서체를 물린다"는 한 줄 안에서
서체가 갈리는 것을 **제어할 수 없게** 만들어서 기각했다(레벨·페이지 번호·좌석 번호까지
전부 갈린다). 남은 것이 "필요한 자리만 `font-mono`" 다.

### 9-1. §4 와의 관계 — mono 의 용도를 넓힌 것이다

§4 는 mono(Source Code Pro)를 **"코드·키·ID"** 용으로 규정한다. 이번 작업은 그 범위를
**수치 주석(금액·상한 카운터·시각)** 까지 넓힌다. 넓힌 이유는 하나다:

> 지금 이 저장소에서 **등폭 숫자를 낼 수 있는 서체가 Source Code Pro 하나뿐이다.**
> 메이플스토리체는 GSUB 가 비어 있어 `tnum` 이 없고 기본 숫자도 비례폭이다(§6-1).

`pipelinepro-DESIGN.md` 는 수정 금지이므로(§4) 그 문서를 고치지 않고 여기에 기록한다.
덧붙여 주차 키(`2026-W34`)는 원래부터 §4 가 말한 **키**에 해당해서, 넓힌 범위가 아니라
원래 규정 안이다.

### 9-2. 판정 기준 — 딱 세 가지만 mono

**바꾼 것**

| 범주 | 예 | 왜 |
|---|---|---|
| **메소 금액** | `3억 2,400만` · 주간 수익 · 분배 몫 | 목록·표로 **세로로 쌓인다.** 자릿수가 어긋나면 금액 비교가 무너진다 |
| **상한 카운터 `X / Y`** | `보스 10/12` · 결정석 `47 / 90` | 상한과의 거리를 눈으로 재는 값이고, 카드가 세로로 반복된다 |
| **시각 · 날짜 · 주차 키** | `8/20 목 21:00` · 눈금 `21:00` · `2026-W34` | 런 시각은 목록으로 쌓이고, 타임테이블 눈금은 가로축에 등간격으로 찍힌다 |

**안 바꾼 것 — 그리고 그 근거**

| 자리 | 판단 |
|---|---|
| 캐릭터 레벨 `Lv.295`, 클래스명 옆 수치 | 발주자 제외 지정. 카드 안 한 줄짜리 표기이고 세로로 비교하지 않는다 |
| 페이지 번호, 선택 인원 `12명 선택` | 발주자 제외 지정. 한 화면에 하나뿐이라 정렬 대상이 없다 |
| 좌석 번호 `#3`, 파티 `3개`, 구성원 `5명` 등 **짧은 배지 숫자** | 발주자 제외 지정. 1~2자리라 어긋나도 눈에 띄지 않는다 |
| 단독 개수 `13건` · `계획 12개` · `클리어 9개` | **상한이 없는 수**다. `X / Y` 와 달리 비교 대상이 없어 정렬이 의미를 갖지 않는다. 대시보드 `주간 보스 10 / 12건` 옆의 `주간+월간 13건` 이 정확히 이 경우라 한 `<dl>` 안에서도 갈렸다 — 의도한 것이다 |
| 90캡 카드의 `주간 12 · 월간 1 · 캐릭터 3명 · 남은 칸 77` | 앞의 수가 한 자리 늘면 뒤가 통째로 밀린다. 어차피 세로로 줄이 서지 않아 mono 로 바꿔도 얻는 것이 없다 |
| 동기화 진행 티커 `갱신 중 3/59` | 한 번 쓰고 사라지는 임시 상태다. 세로로 읽는 값이 아니다 |
| 자격증명 관리의 `마지막 확인 2026. 8. 18. 오후 3:20` | 설정 모달(§1.1.1) 안이고, `오후` 를 포함한 로케일 문자열이라 조각이 많이 난다. 얻는 것보다 얼룩이 크다 |
| 인원 입력칸(`party-size-field`) | 1~2자리 입력이고 값이 하나뿐이다 |

한 줄 요약: **세로로 줄 세워 읽는 숫자만 등폭.** 나머지는 본문 서체를 지킨다 —
필요 없는 자리까지 바꾸면 화면이 두 서체로 얼룩진다.

### 9-3. 한글은 절대 mono 안에 넣지 않는다

Source Code Pro 에는 **한글이 없다.** `보스 10/12` 를 통째로 `font-mono` 로 감싸면
`보스` 가 OS 기본 등폭 서체(윈도우면 굴림체 계열)로 떨어진다 — Outfit/Inter 를 버린
바로 그 증상의 재현이다(§1). 그래서 **숫자 구간만** 감싼다.

구현은 `src/components/domain/numeric.tsx` 두 개다.

| | 용도 |
|---|---|
| `<Numeric>` | 내용이 **순수 ASCII** 일 때. 주차 키, `10/12`, `M/d` 눈금 |
| `<NumericText>` | 한글이 섞인 문자열. 정규식 `/\d+(?:[.,:/-]\d+)*/g` 으로 숫자 구간만 골라 감싼다 |

`NumericText` 가 필요한 이유는 포맷 헬퍼가 한글을 품고 나오기 때문이다 —
`formatKstShort` → `8/20 목 00:00`, `formatMesoCompact` → `3억 2,400만`,
`TimeUntil` → `3시간 20분 뒤`. 통째로 감쌀 수 없고, 그렇다고 호출부마다 문자열을
쪼개면 규칙이 복제된다.

### 9-4. `tabular-nums` 를 지우지 않았다

mono 로 바꾼 자리에서도 `tabular-nums` 클래스를 **남겨 두었다.** Source Code Pro 에서는
모든 글자가 이미 등폭이라 중복이지만, 언젠가 mono 서체가 또 바뀌면(비례 숫자를 가진
서체가 오면) 다시 필요해진다. 지우면 그때 조용히 어긋난다.
해당 지점마다 그 사유를 주석 한 줄로 남겼다.

바꾸지 않은 자리의 `tabular-nums` 도 그대로 둔다. 지금은 아무 효과가 없지만
(§6-1) 지우는 순간 "이 숫자는 정렬이 필요 없다"는 잘못된 신호가 된다.

### 9-6. 함정 — `inline-flex gap-*` 안에서 `NumericText` 를 벌거벗겨 두지 말 것

`NumericText` 는 문자열을 **여러 조각**으로 쪼갠다(`3` / `억 ` / `2,400` / `만`).
부모가 `inline-flex` 에 `gap` 이 걸려 있으면 그 조각 하나하나가 flex 아이템이 되어
**조각 사이에 gap 이 벌어진다.** 실제로 `MesoAmount`(`inline-flex gap-1`)에서
`3억 2,400만` 이 `3 억 2,400 만` 으로, `TimeUntil` 에서 `2일 뒤` 가 `2 일 뒤` 로 나왔다.

해법은 한 겹 더 감싸는 것뿐이다 — `<span><NumericText>…</NumericText></span>` 로 두면
문구 전체가 flex 아이템 하나가 된다. 두 파일 모두 그 `<span>` 옆에 "지우지 말 것" 주석을
달아 두었다. 부모가 `<p>` 나 보통 `<span>` 인 다른 사용처는 인라인 흐름이라 무관하다.

### 9-7. 남은 위험

- **Source Code Pro 는 `next/font/google` 로 받는다.** 빌드 시점에 self-host 되므로
  런타임 외부 요청은 없다(§1 과 동일). 다만 이제 mono 가 **모든 화면**에 등장하므로
  예전보다 일찍 필요해진다 — 지금은 `preload` 를 켜지 않았고, 금액 한 줄이 잠깐 폴백
  등폭으로 보였다가 바뀔 수 있다. 실사용에서 거슬리면 그때 `preload` 를 검토한다.
- **x-height 차이.** 메이플스토리체 0.479em vs Source Code Pro 약 0.486em 으로 거의
  같아 한 줄 안에서 숫자만 커/작아 보이는 현상은 관찰되지 않았다. 다만 `text-caption`
  (12px) 이하에서는 여백 인상이 미세하게 다르다.
